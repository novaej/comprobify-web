## [0.4.0] — 2026-07-06

### Added
- **Subscription and billing management on `/settings/billing`** — a new screen showing the tenant's current plan/quota usage, subscription/payment history, and the actions to act on it: subscribing to a paid tier (`POST /v1/subscriptions`, works even while still in sandbox), changing tier on an `ACTIVE` subscription (`POST /v1/subscriptions/change-tier` — upgrades apply immediately with a prorated charge, downgrades schedule for the end of the current billing period at no cost), and uploading SPI transfer proof (`PATCH /v1/payments/:id/proof`) with bank-transfer details shown alongside. Gated by two new permissions, `billing.read` (view) and `billing.manage` (act) — granted to Owner, Admin, and `BillingOperator` (which previously had neither despite the role name).
- **Real pricing on `/pricing`** — replaced the hardcoded "Sandbox/Starter/Pro, Coming soon" placeholder cards with a Server Component that reads the live tier catalog from the new public `GET /v1/tiers` endpoint (`listTiers()`), so quota/price numbers can never drift from the API's `subscription-tiers.js`. Added a monthly/yearly toggle (yearly = 2 months free) and four tiers (FREE/STARTER/GROWTH/BUSINESS) with feature bullets built from the API response instead of static copy.
- **Tier selection threaded from `/pricing` through registration into production promotion** — picking a paid plan on `/pricing` links to `/register?tier=X&interval=Y`; since actual promotion can happen long after registration, the choice is persisted on `Tenant.intendedTier`/`intendedBillingInterval` (threaded through `registerAction`'s redirect → `/onboarding/tenant` → hidden form fields → `bootstrapTenantAction`) rather than carried as a transient query param. The production-promotion confirm step on `/settings` pre-fills a tier picker from that stored value, editable before confirming, or — if a subscription was already started via `/settings/billing` while still in sandbox — replaces the picker with a note pointing there instead (selecting a tier at promotion would be a silent no-op once a subscription is already `ACTIVE`).

- **Recurring subscription renewals and payment/subscription notifications** — `/settings/billing` now handles a `RENEWAL` payment purpose (opened automatically ~7 days before `current_period_end` by the API's scheduled job, reusing the same proof-upload card as any other payment) and surfaces it correctly in the subscription history. Four new notification types — `PAYMENT_VERIFIED`, `PAYMENT_REJECTED`, `SUBSCRIPTION_RENEWAL_DUE`, `SUBSCRIPTION_EXPIRED` — are now "live" in `/settings/notifications` (previously only `DOCUMENT_AUTHORIZED`/`CERT_EXPIRING`/`CERT_EXPIRED` were) and all route to `/settings/billing` when clicked in the notification bell.
- **Super admin panel at `/admin`** — an internal tool gated by `isSuperAdmin: true` on the `User` row (`requireSuperAdmin()` in `src/lib/admin-context.ts`); redirects anyone else to the dashboard. `/admin/tenants` lists all tenants with inline controls to update their tier (FREE/STARTER/GROWTH/BUSINESS), status (`PENDING_VERIFICATION`/`ACTIVE`/`SUSPENDED`), and trigger tenant verification; `/admin/payments` lists all `REPORTED` payments awaiting proof review with verify and reject (with free-text rejection reason) actions. All mutations call the Comprobify API's `/admin/*` routes via `src/lib/admin-api.ts` using `COMPROBIFY_ADMIN_SECRET`. New `admin.payments` and `admin.tenants` i18n namespaces.
- **Mailgun invite emails** — `inviteUserAction` and `resendInviteAction` (both in `src/app/actions/users.ts`) now send an invitation email to the invited user's address via `src/lib/mailgun.ts`, containing a link to `/complete-registration`. Requires `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, and `MAILGUN_FROM` env vars (already in `.example.env`). Failure is non-fatal — the invite is created in the DB first and the email is best-effort.
- **Owner-role guard on the user role picker** — the role `Select` on `/users` now filters `Owner` out of the assignable options for non-owner users; only an existing `Owner` can promote someone else to `Owner`. Previously any `Admin` could assign `Owner` via the dropdown.
- **Legal agreements gate at `/agreements`** — a new page that checks `GET /v1/tenants/agreements` (`getAgreementStatus()`) on every authenticated session entry; if any TERMS, PRIVACY, or DPA document has been updated since the tenant last accepted, the user is shown a checkbox-per-document acceptance form before the dashboard becomes accessible. `acceptAgreementsAction` calls `POST /v1/tenants/agreements` with the current TERMS version and the browser's `User-Agent` header (forwarded from the BFF so the API records the real client, not the server's Node UA). On success, `revalidatePath('/', 'layout')` clears the gate and redirects to `/dashboard`. New `agreements` i18n namespace; route added to the authenticated-layout guard.
- **SRI rejection messages on Invoice Detail** — when a document is `RETURNED` or `NOT_AUTHORIZED`, the detail page now renders the SRI's raw `rejectionMessages` array (strings returned by `GET /v1/documents/:key`) as an amber warning block above the events timeline, giving users the exact reason the SRI rejected the document without having to search the events log. Previously this data was fetched but never displayed.
- **Issuer activation hint in create-issuer dialog** — the "Nuevo emisor" dialog now shows a persistent info note reminding users to ensure the establishment (`establecimiento`) and issue point (`punto de emisión`) are already created and active in the SRI's portal before issuing documents with the new issuer; SRI-side activation is a prerequisite the API cannot check.

### Changed
- **`POST /v1/tenants/promote` now optionally requests a tier/billing interval** — `promoteTenantAction`/`promoteTenant()` accept and forward `tier`/`billingInterval`, and redirect to `/settings/billing` after promotion when the response includes a `subscription` (a tier was requested, or one was already active).
- **Billing interval change support in the change-tier card** — `/settings/billing`'s "Change tier" section now exposes the API's full three-scenario behavior: same-interval upgrade (immediate prorated charge), same-interval downgrade (scheduled, no payment), and any billing-interval change (deferred to `current_period_end`, billed at the full new price). `changeTierAction` now accepts an optional `billingInterval` and forwards it to `POST /v1/subscriptions/change-tier`. `ApiPaymentInfo` gains `target_billing_interval` (returned when the interval also changes) and the subscription history labels those payments with the interval alongside the tier name.
- **Subscribe and change-tier cards redesigned as card grids** — replaced the tier `Select` dropdown with a visual card grid (one card per paid tier, showing name, price for the selected interval, IVA note, and document quota) backed by the same `IntervalToggle` pill used on `/pricing`. On the change-tier card the current plan is marked as locked/greyed when the current interval is selected; switching interval while keeping the same tier is a valid selection (triggers the interval-change scenario). Same-tier, same-interval is a no-op with an inline hint.
- **Payment amount display simplified** — the pending-payment card previously showed a two-line breakdown (`Monto a transferir` / `Base imponible + IVA`). Now shows only the IVA-inclusive total with an inline "IVA incluido" label; the breakdown was considered confusing without adding actionable information.
- **Payment rejection reasons are now localized** — `ApiPaymentInfo.rejection_reason` (free-text string) replaced by `rejection_reason_code` (enum); the frontend maps the code through a new `billing.rejectionReason.*` i18n namespace with user-friendly messages for `AMOUNT_MISMATCH`, `TRANSFER_NOT_FOUND`, `WRONG_ACCOUNT`, `ILLEGIBLE_PROOF`, `DUPLICATE_SUBMISSION`, and `OTHER`.
- **FREE tier renamed to "Gratis" / "Free" on `/pricing`** — the name "Sandbox" was dropped to avoid implying the free tier is a development-only environment; the tier's actual test-environment behavior is described in the card's marketing blurb instead. The FREE card also now shows `$0` with no period suffix (previously incorrectly showed `$0/mes`).

### Fixed
- **`Tenant.pendingBankTransfer` was cleared as soon as a payment verified, leaving every later renewal with no bank details to show** — the cached bank-transfer info is static, env-configured data on the API (identical for every tenant and every payment), and a renewal payment is opened by a backend cron job with no frontend call that could ever repopulate it. `/settings/billing/page.tsx` now keeps the cache indefinitely instead of clearing it after the first payment.
- **`ApiSubscriptionInfo.status` and `ApiPaymentInfo.purpose` only covered the happy-path values** — the API's `chk_subscriptions_status` constraint also allows `PAYMENT_RECEIVED` (briefly set between a verified payment and its invoice being linked) and `EXPIRED`/`SUSPENDED`, none of which were in the frontend's type or `billing-manager.tsx`'s status-badge/styling maps; `purpose` was missing the new `RENEWAL` value. All three now degrade to a generic badge instead of being possible at all to hit unhandled.
- **Pricing page showed `/mes` for all paid tier cards even when "Yearly" was selected** — the period suffix was accidentally hardcoded to `/mes` during the FREE tier rename; now correctly shows `/mes` or `/año` based on the active toggle.
- **Register page "Volver" went to the landing page even when arriving from `/pricing`** — the back link was hardcoded to `/`; it now resolves to `/pricing` when `?tier=` is present in the URL (i.e. the user clicked a paid CTA on the pricing page).
- **Production promotion sequential inputs were not per-issuer** — the sequential form on `/settings` previously showed a single flat list of document-type/number pairs, with `promoteTenantAction` incorrectly flat-mapping the same values onto every issuer; a tenant with multiple issuers would apply the first issuer's starting sequentials to all of them. Inputs are now grouped by issuer (showing each issuer's name as a section header), and `promoteTenantAction` passes per-issuer sequentials directly to `POST /v1/tenants/promote`.
- **Subscription detection on promotion was too narrow** — the check that suppresses the tier picker and prevents passing a tier to `promoteTenant` only matched `status === 'ACTIVE'`, so a subscription in `PAYMENT_RECEIVED` or `INVOICE_PROCESSING` state (briefly set between payment verification and invoice linking) was not detected as in-flight. `promoteTenant` would then attempt `createSubscription` for the requested tier, which the API rejected as `SUBSCRIPTION_ALREADY_IN_FLIGHT` — after sandbox keys were already revoked, leaving the tenant unable to complete promotion. The check now matches any subscription status that is not `CANCELLED` or `EXPIRED`; when an in-flight subscription is detected, `tier`/`billingInterval` are omitted from the promote call and the UI shows the in-flight tier name instead of the tier picker.

## [0.3.0] — 2026-06-27

### Added
- **Full issuer CRUD on `/issuers`** — a "Nuevo emisor" dialog creates either a new branch or a new issue point under an existing branch (both go through the same `POST /v1/issuers`, distinguished by `branchCode` reuse), a new `/issuers/:id` edit page consolidates trade name/branch address editing, logo, and certificate renewal (moved off the list cards), and each card now has an Active/Inactive toggle for soft-delete/reactivate instead of a one-way delete. New `comprobify` endpoints: `PATCH /v1/issuers/:id` (trade name/branch address), `DELETE /v1/issuers/:id` (soft-delete, guarded against removing the last active issuer or one with documents), `PATCH /v1/issuers/:id/activate` (reactivate, re-checking plan tier limits). New local `Issuer.active` column, filtered everywhere a tenant's issuer set is resolved except `/issuers` itself, which shows both states so the toggle has something to act on.
- **Manual sequential correction per document type/environment** — `/issuers/:id` shows each enabled document type's current/next sequential for sandbox and production side by side, with an edit dialog gated to whichever environment matches the tenant's current `environment` (editing the dormant one wouldn't affect any real document). Backed by new `GET`/`PATCH /v1/issuers/:id/sequentials[/:documentType]`, the latter rejecting a `nextSequential` that doesn't exceed the current value (`SEQUENTIAL_CANNOT_DECREASE`) under a `FOR UPDATE` lock so it can't race a concurrent document creation into a duplicate sequential.
- **Canonical in-app webhook moved from onboarding to `/settings/webhooks`** — real-time notification delivery is no longer auto-registered during tenant bootstrap (silently skipped/failed if `NEXT_PUBLIC_APP_URL` wasn't set at that exact moment); a dedicated "Activar"/"Desactivar" control reuses the same API-side webhook endpoint row across toggles (`PATCH` to flip `active`) instead of creating a new one each time, and detects when `NEXT_PUBLIC_APP_URL` isn't a publicly-reachable HTTPS URL (e.g. local dev) before offering a button that would otherwise fail validation.
- **Clickable notifications** — clicking a notification now navigates to what it's about (a single authorized document → its detail page, an aggregated batch → the documents hub, a certificate alert → the issuer list) instead of only offering "mark read", via a new `getNotificationHref()` mapping verified against the actual metadata shapes `comprobify`'s notification service writes.

### Fixed
- **`createBranchAction` sent business data the API silently ignored, and could diverge from what was actually stored** — `createIssuer()` posted `ruc`/`businessName`/`tradeName`/`mainAddress`/`emissionType`/`requiredAccounting`, none of which `issuerService.createBranch` reads (it always inherits these from the source issuer); the local DB write used the form's input instead of the API's response, so a typed value could silently differ from what the API actually stored. Now sends only the fields the validator actually checks and writes the local row from the API's response.
- **Uploading a P12 with no password during issuer creation silently dropped the certificate file** — `createIssuer()` only appended the `cert` file `if (p12 && p12Password)`, so a P12 with an empty password never made it into the request at all.
- **A deactivated issuer could still be auto-selected or counted as available** — `requireContext()`'s `getAccessibleIssuers`/ownership check, the locale layout's issuer list, `/issuer/select`, `/settings`, `/users`, `postLoginRedirect`'s `_count.issuers` (a tenant with one deactivated issuer among several was wrongly sent to the multi-issuer picker), and tenant promotion's sequential seeding all now filter on `Issuer.active`.

## [0.2.0] — 2026-06-24

### Added
- **App version shown in the sidebar** — a small `v{version}` line below the user menu, reading `package.json`'s version directly (`src/app/[locale]/layout.tsx` imports it and passes it down as a prop) so it never has to be updated by hand or via an env var.
- **Document type column on the dashboard's recent-documents table** — since that table mixes invoices, credit notes, and other types together (unlike `/documents/[type]`, which is already filtered to one type), each row now shows a "Tipo" column. `DocumentTable` (`src/components/document-table.tsx`) takes an optional `typeName` resolver prop to render it — omitted on `/documents/[type]` where it would be redundant.
- **Credit notes can't exceed the original invoice's remaining (uncredited) balance, and their buyer identity is locked to the original's buyer** — new `GET /v1/documents/:key/credit-notes` API endpoint (`getCreditNotesBalance()` in `src/lib/api.ts`) sums every `AUTHORIZED` credit note already referencing a document and returns the remaining creditable balance. `CreditNoteForm` shows it, disables submission with a destructive warning when the live total would exceed it, and re-checks it server-side in `createCreditNoteAction`/`rebuildCreditNoteAction` (`assertWithinRemainingBalance`) as defense-in-depth against a stale client. Buyer `idType`/`id`/`name` become read-only once an original document is selected — a credit note must legally apply to the same buyer as the invoice it credits (`address`/`email` stay editable). Also added a hint clarifying that only invoices created in this system can be selected — there's no SRI or API service that can look up a document issued elsewhere (confirmed against `../comprobify/src/services/sri.service.js`: SRI only exposes submit + authorization-by-known-access-key, never a search by buyer/date/number).
- **Credit note (Nota de Crédito, document type `04`) creation** — new `CreditNoteForm` (`src/components/credit-note-form.tsx`) and `/credit-notes/new` route, kept separate from `InvoiceForm` since the request shape differs too much to share (no `payments`; instead `originalDocument: { documentType, number, issueDate }` and `motivo`). `CreateCreditNotePayload` added alongside `CreateInvoicePayload` as a discriminated union (`CreateDocumentPayload`) in `src/lib/api.ts`. Two entry points converge on `getInvoiceForCreditNoteAction` (`src/app/actions/credit-note.ts`): a "Crear nota de crédito" item in the Invoice Detail actions menu for `AUTHORIZED` type-`01` documents (`?fromInvoice=<accessKey>`), and a "Buscar comprobante" picker inside the form itself for the documents-hub entry point (`searchCreditableInvoicesAction`, filtering `listDocuments` to `documentType: '01', status: 'AUTHORIZED'`). Since the API has no lookup-by-number endpoint, `originalDocument.number` (`NNN-NNN-NNNNNNNNN`) is always reconstructed server-side from the issuer's `branchCode`/`issuePointCode` + the document's `sequential`, never typed by hand. All pre-filled fields except buyer identity stay editable, so a credit note that doesn't track specific products (a flat monetary adjustment) works by replacing the items with a manual entry. Supports the same rebuild (`?rebuild=`) and sign-only/sign-and-send dual-submit flow as invoices. `ProductSearch` was extracted out of `invoice-form.tsx` into its own `src/components/product-search.tsx` so both forms share the catalog-product autocomplete instead of duplicating it.
- **Actions column on document list tables** — `DocumentTable` (shared by `/documents/[type]` and the dashboard's recent-documents preview) gained an "Acciones" column with two icon buttons — download PDF (RIDE) and download XML — shown for `AUTHORIZED` documents, using the same `/api/documents/:key/ride`/`xml` routes and status gating already used on Invoice Detail.
- **Specific event messages and status-transition columns in Invoice Detail history** — the events table previously showed the raw `eventType` (e.g. "Estado actualizado" for every `STATUS_CHANGED` row) with no indication of what actually changed, even though the API already returns `fromStatus`/`toStatus`. New `describeDocumentEvent()` (`src/lib/event-description.ts`) maps each known `eventType` to a specific title (e.g. "Autorizado por el SRI" / "No autorizado por el SRI" instead of a generic status update), verified against every `documentEventModel.create()` call site in the API. Dedicated "Estado anterior"/"Estado nuevo" columns render each side of a transition as a colored `StatusBadge`, and the authorization number is shown with a copy button instead of buried in a generic detail column. (SRI's actual rejection *reason text* still isn't shown — it's stored in a `sri_responses` table the API never exposes via any endpoint; rejections show only the status code.)
- **Certificate renewal on `/issuers`** — a "Renovar certificado" dialog per issuer card (Owner/Admin, `issuers.manage`) lets a tenant replace an issuer's P12 certificate without recreating the issuer, e.g. when it has expired or is expiring soon. Calls the new `PATCH /v1/issuers/:id/certificate` endpoint (multipart `cert` file + optional `certPassword`) via `renewIssuerCertificate()` in `src/lib/api.ts` and `renewIssuerCertificateAction` in `src/app/actions/issuers.ts`, then `revalidatePath('/issuers')` so the updated expiry/fingerprint show immediately. Renewal only affects future signing — each already-signed document embeds its own certificate copy inside the XML signature, so past invoices are unaffected. The password field is optional per the API contract (some P12 archives have none), but a hint under the field warns that upload fails if the certificate needs one and it's left blank.
- **Fixed: malformed invoice access key showed the generic error page instead of 404, and `ApiError.isValidation()` never returned true** — `invoices/[key]/page.tsx` only treated `err.isNotFound()` as "not found"; a wrong-length/non-numeric access key in the URL returns the API's `VALIDATION_FAILED` error instead of `NOT_FOUND`, so it fell through to `error.tsx`. Tracing it down also surfaced a pre-existing bug in `src/lib/errors.ts`: `isValidation()` checked `this.status === 422`, but `../comprobify/src/errors/validation-error.js` returns HTTP **400** for `VALIDATION_FAILED` (and 400 is shared with several unrelated codes like `ISSUER_ID_REQUIRED`/`INVALID_STATE_TRANSITION`, so the fix checks `this.code === 'VALIDATION_FAILED'`, not status). Since `key` is the only param `getDocument()`/`getDocumentEvents()` validate, a validation error on this route can only mean a malformed access key — now also caught and routed to `notFound()`.
- **Locale-aware 404 page** — `src/app/[locale]/not-found.tsx` renders a translated "Page not found" UI with a link back to the dashboard, replacing Next.js's default unstyled 404 for unmatched routes and explicit `notFound()` calls (e.g. a missing invoice on Invoice Detail). New `notFoundPage` i18n namespace. Doesn't cover an invalid `:locale` URL segment itself — see CLAUDE.md Common Mistake #29. Its back-to-dashboard link uses a plain `<a>` tag instead of the app's `Link` component, since client-side navigation from a `notFound()` boundary silently fails to navigate in the Next.js App Router (see Common Mistake #30).
- **Loading skeletons for Dashboard and Invoice Detail** — `src/app/[locale]/dashboard/loading.tsx` and `src/app/[locale]/invoices/[key]/loading.tsx` render shadcn `<Skeleton>` placeholders shaped like each page's actual layout (KPI cards + table rows; header + info grid + events table) while their Server Components fetch, replacing the previous blank screen during navigation.
- **Error boundary for `[locale]` segment** — `src/app/[locale]/error.tsx` catches unhandled Server Component errors and shows a friendly page (icon, generic `apiError.UNKNOWN` message, "Retry"/"Back to dashboard") instead of the framework's blank crash screen. Reports to Sentry via `Sentry.captureException` (same pattern as the existing root `global-error.tsx`). New `errorBoundary` i18n namespace. Note: the specific API error code does not survive the server→client error-boundary serialization, so the message shown is always the generic fallback, not the original `ApiError.code`.
- **PDF preview on Invoice Detail for AUTHORIZED documents** — a "Vista previa PDF" toggle button lazy-mounts an embedded `react-pdf` viewer pointed at the existing `/api/documents/:key/ride` download route (no new endpoint), with a `ResizeObserver`-driven responsive width and Previous/Next controls for multi-page PDFs. New `src/components/invoice-pdf-preview.tsx`, `invoice-pdf-preview-lazy.tsx` (the required `next/dynamic(..., { ssr: false })` Client Component wrapper — Turbopack's production build rejects that option inline in a Server Component), and `invoice-pdf-preview-toggle.tsx`. New deps: `react-pdf` (MIT), `pdfjs-dist` (Apache-2.0, transitive).
- **Rebuild ("Corregir") button for RETURNED/NOT_AUTHORIZED invoices** — Invoice Detail now shows a "Corregir" button for documents the SRI rejected, linking to `/invoices/new?rebuild=:accessKey`, which reuses the create form pre-filled from the document's stored `requestPayload` (new `requestPayloadToFormValues()`, the inverse of the existing create-payload builder). Submitting calls the new `rebuildInvoiceAction` → `POST /v1/documents/:key/rebuild` (same accessKey/sequential, status back to `SIGNED`), sharing the same sign-only / sign-and-send dual-button pattern as invoice creation, just relabeled "Corregir" / "Corregir y Enviar". New `Document.requestPayload` field and wired-up `rebuildDocument()` in `src/lib/api.ts`.
- **Fixed: Invoice Detail's back-link always showed "Panel" after creating or correcting a document** — `createInvoiceAction`/`rebuildInvoiceAction`'s post-submit `redirect()` carried no `?from=` query string, so the `?from=`-based back-link always fell back to its `dashboard` default regardless of where the user actually started (e.g. a per-type document list). Both actions now take a `from?: BackTargetKey` parameter, threaded from the page's own validated `backTargetKey` through `InvoiceForm`, and for the rebuild loop specifically also threaded from Invoice Detail's own `from` through the "Corregir" link. Also fixed the form's bottom "Volver" button, which was hardcoded to `/dashboard` regardless of context — it now uses the same `backHref` the page computes for its header back-link.
- **Sign-only submit on invoice creation** — `/invoices/new` now has two submit buttons: "Firmar y Enviar" (existing behavior — sign and immediately attempt SRI submission) and a new "Firmar" button that signs the document but explicitly skips `sendToSri()`, leaving it in `SIGNED` status. Both share the same confirmation dialog, which swaps its title/description/icon based on which button was clicked. `createInvoiceAction` takes a new `sendAfterSigning: boolean` parameter to gate the send step. A signed-only document is sent later from the existing "Enviar" recovery button on the Invoice Detail page — no new follow-up screen needed.
- **Sorting and filtering on `/documents/[type]`** — Número, Cliente, Fecha, and Estado are now sortable (clickable column headers) and filterable (debounced contains-search on Número/Cliente, a calendar date picker for Fecha, a status select), all stored in the URL and composed correctly with pagination via a shared `buildHref()` helper. New `src/components/document-filters.tsx`; backed by new `sortBy`/`sortDir`/`sequential`/`buyerName` query params on `GET /v1/documents` in `comprobify`. Added a distinct "no results match your filters" empty state (`documents.list.emptyFiltered`) separate from the generic fetch-error message.
- **Dashboard KPI summary cards** — `/dashboard` now shows issued-this-month (by type), net authorized revenue this month (`FAC + LIQ + DEB − CRE`), and an all-time needs-attention count, backed by a new `getDocumentStats()` call to `GET /v1/documents/stats`. The document table below is capped to 10 rows with a "Ver todos" link to `/documents` instead of loading up to 50 rows unpaginated. New `src/components/dashboard-summary-cards.tsx`.
- **Pagination on `/documents/[type]`** — the per-type document list (e.g. `/documents/01`) now pages through results 20 at a time via a `?page=` query param instead of silently truncating at 50, using the `pagination` object already returned by `listDocuments()`. New `src/components/document-pagination.tsx` (generic; reusable by future paginated lists) and `src/components/ui/pagination.tsx` (shadcn).
- **Issuer cert info + logo editing on `/issuers`** — each issuer card now shows its signing certificate's expiry date and fingerprint (fetched via `listTenantIssuers()`, which already returned this data but was unused), color-coded amber/red using the same day thresholds the API uses for `CERT_EXPIRING`/`CERT_EXPIRED` notifications. Added a "Cambiar logo" dialog (Owner/Admin only) backed by the new `uploadIssuerLogo()` in `src/lib/api.ts` and `updateIssuerLogoAction` in `src/app/actions/issuers.ts`, calling `PATCH /v1/issuers/:id/logo` — the only field the Comprobify API allows updating on an existing issuer.
- **Invoice templates** — "Save as template" / "Load template" on the New Invoice form let users save a complete invoice (buyer, line items, payment methods, additional fields) and reload it later instead of re-entering everything. Backed by a new `DocumentTemplate` Prisma model (migration `20260622014656_add_document_templates`), scoped per tenant, with a generic `documentType` column (defaults to `'01'`/invoices) so other SRI document types can reuse it once they get a create flow. Loading shows a preview (buyer, item descriptions, total) so similarly-named templates stay distinguishable; saving over an existing name shows an inline overwrite warning instead of erroring silently. New `src/app/actions/templates.ts` (`listInvoiceTemplatesAction`, `saveInvoiceTemplateAction`, `deleteInvoiceTemplateAction`).
- **Automatic Prisma migrations on deploy** — new `vercel-build` script (`prisma generate && prisma migrate deploy && next build`); Vercel auto-detects and runs it instead of `build`, so every staging/production deploy applies pending migrations before building. `prisma migrate deploy` skips already-applied migrations, so it's a no-op on deploys with no schema change.
- **Link an existing Comprobify API account during onboarding** — `/onboarding/tenant` now offers a second tab alongside "Create new company": paste an existing API key to link that tenant instead of registering a new one. Uses the new `GET /v1/tenants/me` endpoint plus `GET /v1/issuers` to resolve tenant/issuer identity, then mints a fresh dedicated key via `POST /v1/keys` (the pasted key is never stored). `Tenant.apiTenantId` is unique, so an API account can only be linked once; the first linker becomes Owner and invites teammates via the existing `/users` flow. ### Fixed
- **`addIssuerDocumentType()` sent `{ code }` instead of `{ documentType }`** — the API's `addDocumentTypeValidator` validates a field named `documentType`, so every attempt to enable a new document type on an existing issuer via `/issuers` (e.g. enabling `04`/Nota de Crédito) silently failed with `VALIDATION_FAILED`. Pre-existing, unrelated to any specific feature — issuers already have type `01` enabled at creation, so this path had never been exercised before. Also added a confirmation dialog before enabling a type, matching the confirm-dialog pattern used elsewhere in the app.
- **`Pagination.totalPages` was a non-existent API field** — `src/lib/api.ts`'s `Pagination` interface declared `totalPages: number`, but the Comprobify API's `GET /v1/documents` only ever returns `{ total, page, limit }`. No caller read `.totalPages` until the new `/documents/[type]` pager (above), at which point it silently evaluated to `undefined` — the "hide on one page" guard (`undefined <= 1` is `false` in JS) never fired, so pagination controls always rendered, and the "Página X de Y" label showed a blank page count. Removed the field; `totalPages` is now derived client-side via `getTotalPages({ total, limit })` in `src/components/document-pagination.tsx`.
- **Onboarding forms flashed a stray error message before redirecting on success** — `IssuerSetupForm` and `LinkExistingAccountForm` caught the `NEXT_REDIRECT` throw from their Server Action (`bootstrapTenantAction`/`linkExistingTenantAction` both end with `redirect()`) as a generic error and briefly rendered "UNKNOWN" before the redirect completed. Both now re-throw the digest-tagged redirect error instead of swallowing it.
- **Several other swallowed-error catch blocks left no trace in Sentry** — same gap as the onboarding fix above, audited across `src/app/actions/`: `auth.ts`'s `completeRegistrationAction`/`registerAction` fallback catches around `signIn()` (these happen after the password/account write already committed), plus the intentionally non-fatal best-effort catches in `onboarding.ts` (webhook registration), `notifications.ts` (catch-up poll), and `webhooks.ts` (onboarding-tail webhook registration) — all now call `Sentry.captureException` so a systemic failure is visible instead of indistinguishable from working.
- **Onboarding DB-write failures left no trace in Sentry** — `bootstrapTenantAction` and `linkExistingTenantAction` caught their post-API-call transaction errors and returned a generic `DB_WRITE_FAILED` code without re-throwing, which is correct (avoids a crash page after the external Comprobify API key was already minted) but also opts out of `onRequestError`'s automatic capture. Both catch blocks now call `Sentry.captureException(err)` explicitly.
- **Sentry build failed source map upload with `Project not found`** — `org` in `next.config.ts` was set to the numeric ID embedded in the DSN hostname (`o<id>.ingest...`) instead of the organization slug; corrected to the actual slug.
- **Sentry config warnings on every build** — removed `disableLogger` and `automaticVercelMonitors` from `withSentryConfig()`; both are deprecated and their suggested `webpack.*` replacements are explicitly unsupported under Turbopack (which this project builds with), so neither the old nor new option does anything.
- **`.example.env` was missing `ENCRYPTION_KEY` and had the wrong generate command for `CONTEXT_COOKIE_SECRET`** (`-base64 32` instead of `-hex 32`) — likely cause of a staging incident where `ENCRYPTION_KEY` was set to a base64 value; `getKey()` in `src/lib/crypto.ts` requires exactly 64 hex characters and throws otherwise.
- **`COMPROBIFY_API_URL` with a trailing slash caused a silent double-slash 404** — requests became `...com//v1/...`, which the API's router doesn't match; it falls through to a generic HTML 404 instead of a JSON error, crashing `JSON.parse` on the client. Documented as a deploy troubleshooting entry; no code change (the fix is removing the trailing slash from the env var).
- **`ApiIssuer` interface didn't match the API's actual `GET /v1/issuers` response** — declared `id: number` (it's a `BIGSERIAL`, serialized as a JSON string) and a phantom `environment` field that the API never returns (environment is tenant-level, not issuer-level); now matches `issuer.service.js → listIssuers()` exactly, including the previously-missing `certFingerprint` / `certExpiry` fields
- **Invited users could not authenticate** — `authorize()` returns `null` for users with no `passwordHash`, causing `signIn()` to throw `AuthError` and fall through to `INVALID_CREDENTIALS`; fixed by pre-checking `inviteStatus` before `signIn()` and redirecting to `/complete-registration` when appropriate
- **Notification `issuerId` matched against wrong field** — cert-expiry banners now compare `notification.issuerId` (API-side BIGSERIAL) against `Issuer.apiIssuerId`, not the local Prisma `Issuer.id`
- **`appUrl` variable conflict in onboarding.ts** — second `const appUrl` declaration renamed to `webhookAppUrl`
