# ADR-007: UUID Primary Keys for Local Tables

**Status:** Accepted  
**Date:** 2026-07-21

## Context

Every table in `prisma/schema.prisma` used `Int @id @default(autoincrement())`. That is fine while the app is a single database on a single host, but it carries costs that only get more expensive to undo:

- **Enumerable identifiers.** Sequential ids leak row counts and make neighbouring records guessable. Every id that reaches the browser (route params like `/issuers/3`, form values, server action arguments) is a small information leak, and authorization bugs become trivially exploitable by incrementing a number.
- **Merge hazards.** Sequential keys collide across environments. Copying a tenant between databases, seeding a staging environment from a dump, or ever sharding by tenant all require an id remap.
- **Ids can't be generated before the insert.** An autoincrement id only exists after the row is written, which rules out building an object graph client-side or in a transaction before persisting it.

The alternative — migrating later, once real tenants exist — means a multi-step online migration per table (add parallel `uuid` column, backfill, add parallel FK columns, repoint, swap, drop) with a deploy plan and a window where both key types are live. Doing it while no deployed database holds data worth keeping is dramatically cheaper.

Four columns mirror the **Comprobify API's own** ids (`Tenant.apiTenantId`, `TenantApiKey.apiKeyId`, `Issuer.apiIssuerId`, `Notification.issuerId`). The first version of this ADR asserted those were `BIGSERIAL` and had to stay `Int`. **That was wrong.** The API is UUID-keyed on every table — `id UUID PRIMARY KEY DEFAULT uuid_generate_v7()` in its `db/migrations/001_create_issuers.sql`, `023_create_api_keys.sql`, `035_tenants.sql`, `044_notifications.sql`, `052_subscriptions_and_payments.sql` — and it validates ids with `param('id').isUUID()`. The claim came from CLAUDE.md's Common Mistake #16, which was itself never verified against the API's SQL.

## Decision

Local primary keys and every foreign key pointing at one become **`String @id @default(uuid(7)) @db.Uuid`**. The four columns mirroring API-side ids are `@db.Uuid` as well, storing the API's value verbatim, and **no id anywhere is ever passed through `Number()`**.

**UUIDv7, not v4.** v7 is time-ordered, so inserts land at the right-hand edge of the B-tree the way an autoincrement key does. Random v4 keys scatter writes across the index and cause page splits and cache churn. v7 keeps the locality benefit that was the main thing sequential ids had going for them.

**Generated by Prisma, not the database.** `@default(uuid(7))` means the application produces the value, so the columns carry no SQL `DEFAULT`. Any writer bypassing Prisma must supply an id. This was the accepted tradeoff for v7 — Postgres has no built-in `gen_random_uuid_v7()` before v18, and `gen_random_uuid()` would have meant v4.

**The resulting invariant, which is the part worth remembering:**

> Every id is a UUID string. Local ids and API ids are therefore *indistinguishable to the compiler*, and telling them apart is a matter of reading the call site.

Anything passed to `src/lib/api.ts` or `src/lib/admin-api.ts` is an API id (`ApiCtx.issuerId`, admin `paymentId` / `subscriptionId` / agreement ids). Anything in a Prisma query is a local id. `Context.issuer` deliberately exposes **both** — `id` (local) and `apiIssuerId` (API-side) — so call sites must pick deliberately.

**Migration is destructive.** `20260721000000_uuid_primary_keys` drops and recreates all 12 tables rather than backfilling. This was safe only because no deployed database held data worth preserving; the SQL carries a comment saying not to reuse the approach.

## Consequences

- **A latent bug was caught in passing.** `fanOutReads()` — in both `src/app/actions/notifications.ts` and `src/app/api/webhooks/receive/route.ts` — compared `Notification.issuerId` (API-side) directly against `UserIssuerAccess.issuerId` (a local FK). Issuer-scoped notifications fanned out to the wrong users, or none. This is CLAUDE.md Common Mistake #20. It briefly became a type error during the migration, while `Notification.issuerId` was still `Int` and the local FK had become `uuid` — that is how it was found. **Once the mirror columns were corrected to `uuid`, the original code would compile again**, which is precisely why this class of bug has to be caught by review. Both call sites now resolve API → local through `Issuer.apiIssuerId` first.
- **The type system does not guard this at all.** Because local and API ids are the same type, passing one where the other belongs compiles cleanly and fails at runtime — or worse, silently matches no rows. Mistake #20 is now enforceable only by review, which is why `Context` names the two fields differently (`id` vs `apiIssuerId`) and why the mirror columns keep the `api` prefix.
- **`Number()` on an id is always a bug.** It yields `NaN`, Prisma rejects it, and the user sees an opaque internal error. This is not hypothetical: it is what broke tenant onboarding (`Number(result.tenant.id)` → `apiTenantId: NaN` → `DB_WRITE_FAILED`) and every admin payment/tenant action until this ADR's correction.
- **Route params need shape-checking.** A malformed `:id` segment reaching a `uuid` column throws a Prisma validation error mid-render instead of letting the page call `notFound()`. `isUuid()` (`src/lib/utils.ts`) guards these — it replaced the `Number.isInteger()` check on `/issuers/[id]`.
- **State minted before the change had to be invalidated.** The `comprobify_ctx` cookie went to `v: 2` with a string `issuerId`, and `readCtxCookie()` rejects anything else, so a stale v1 cookie redirects to the issuer picker. `isUuid()` also guards `session.user.id` everywhere it reaches Prisma, so a JWT holding an old integer user id bounces to `/login` instead of crashing every authenticated page load.
- **Ids are 16 bytes instead of 4**, in the PK and in every FK and index that references it. At this application's row counts the storage and index-depth cost is not a consideration.
- **The frontend and API now share one id space.** An id copied from an API response into a local mirror column needs no conversion in either direction, which removes a whole class of coercion bug — at the cost of the ambiguity described above.
- **Ids are no longer human-quotable.** "Tenant 42" in a support conversation becomes a 36-character string. Business identifiers people actually cite (RUC, access key, invoice number) were never the primary key, so this mostly affects internal debugging.
