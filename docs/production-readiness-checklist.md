## Security & CI hardening

The Comprobify API repo ran a first holistic security audit (`../comprobify/docs/security-audit-2026-09-12.md`, PR #213) across CI/CD, deployment infrastructure, and application code. This app never had an equivalent pass — the items below are what a parallel check surfaced here, grouped by whether they were fixed as part of that check or are still open. Several are mechanical fixes mirroring the API repo's own resolutions exactly; a few are genuinely different because this repo's situation differs (private vs. public repo, real vs. clean `npm audit` findings, no existing test suite).

**Fixed:**

- [x] **`scripts/rotate-encryption-key.js` no longer accepts `OLD_ENCRYPTION_KEY`/`NEW_ENCRYPTION_KEY` as env vars or CLI args.** This is the incident-response tool for a suspected key compromise — the old version took both keys via `docker compose exec -e KEY=value`, landing them in shell history and the droplet's process list, on the exact droplet an attacker with residual access might be watching. Now prompts interactively with hidden input, fails fast if stdin isn't a real TTY. `docs/guides/encryption-key-rotation.md` updated to the `docker compose exec -it` invocation this requires. Mirrors the identical fix in the API repo (its finding #3)
- [x] **Third-party GitHub Actions pinned to commit SHAs, not mutable version tags** — `appleboy/scp-action`, `appleboy/ssh-action` (both handle `INFRA_SSH_PRIVATE_KEY` and write the droplet's entire `.env`), and `hashicorp/setup-terraform` (runs inside jobs holding `DO_TOKEN`/`CLOUDFLARE_TOKEN`) across `deploy-staging.yml`, `deploy-production.yml`, and all 4 `terraform.yml` job steps. A compromised maintainer account re-pointing a tag could otherwise exfiltrate every secret with no diff in this repo to catch it in review. Mirrors the API repo's finding #4
- [x] **Docker base images pinned by digest, not mutable tags** — `node:24-slim` (all three `Dockerfile` stages) and `caddy:2-alpine` (`deploy/docker-compose.yml`), resolved via `docker buildx imagetools inspect`. A tag can be rebuilt upstream with different contents at any time, silently changing what ships between builds with nothing in this repo's diffs to catch it. Mirrors the API repo's finding #5 (this app has no Redis/worker, so only these two images apply, vs. the API's three)
- [x] **Both deploy workflows scan the built image with Trivy** (`aquasecurity/trivy-action`, SHA-pinned) between `docker build` and `docker push`. **Deliberately informational only for now** (`exit-code: '0'`) — the current base image baseline hasn't been triaged yet (see the open item below), and making it block immediately would red-X the first real deploy for findings nobody's reviewed
- [x] **New `.github/workflows/ci.yml`** runs `npm run type-check` and `npm audit --omit=dev --audit-level=high` on every PR/push to `main`. This repo has no test suite to run (`package.json` has no `test` script — see `docs/guides/encryption-key-rotation.md`'s note on the same gap), so type-checking is the closest available correctness gate, not a unit suite the way the API repo's `ci.yml` runs one. **The audit step uses `continue-on-error: true`, not a hard failure** — unlike the API repo, a real run here found active HIGH/CRITICAL findings in production dependencies themselves (see below), not just a dev-only build toolchain; making it blocking today would red-X every PR immediately
- [x] **New `.github/dependabot.yml`** — npm (grouped weekly PRs; `next`, `next-auth`, `@auth/core`, `prisma`/`@prisma/*` excluded from the group, both because they're load-bearing and because they're currently carrying real findings that need individual review) and github-actions (keeps the SHA-pinned actions current; `appleboy/*` excluded from the group since a behavior change there wouldn't surface until a real deploy runs)
- [x] **GitHub Environment protection rules added to both `staging-infra` and `production-infra`** — required-reviewer rule (`pandc19`, `can_admins_bypass: false`), live-verified via `gh api`. Getting there required making `novaej/comprobify-web` **public** (same GitHub Team billing-plan quirk the API repo hit); a full git-history secret scan was run before accepting that — clean, see the `production-infra` item above for what was checked
- [x] **`docker login` no longer exposes `GITHUB_TOKEN` via the droplet's process list** — fixed here even though it's still open in the API repo (was tracked as "parity, not urgency," but the fix turned out to be simple enough to just do). `echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io ... --password-stdin` put the token in `echo`'s own argv, visible via `ps` on the droplet for the run's duration. Also added `docker logout ghcr.io` immediately after `docker compose pull` (the only step needing registry auth — `up`/`exec` don't), clearing the token back out of `~/.docker/config.json` instead of leaving it there indefinitely between deploys

## Staging lifecycle once production is live

**Decided and done, mirroring the API repo's own end state exactly.** Staging's droplet is destroyed — live-verified: `dig staging.comprobify.com`/`dig app-staging.comprobify.com` both resolve to nothing (Terraform-managed Cloudflare A records are gone along with the droplet), and a health-check request can't even resolve the host. `STAGING_INFRA_ENABLED` (repository variable) is `false`, live-verified — `terraform.yml`'s `plan-staging`/`apply-staging` jobs stay skipped rather than trying to reconcile infra that no longer exists.

`deploy-staging.yml` is disabled (`if: false`, `push` trigger commented out) — same reasoning as the API repo's own identical disabling: with no droplet to SSH into, every run would just fail trying to reach a `DROPLET_IP` that resolves to nothing. **`release-staging.yml` stays fully enabled** — it only fast-forwards the `staging` git branch on a tag push, harmless bookkeeping independent of whether a droplet exists, exactly matching the API repo's own reasoning for keeping it on.

**The re-provisioning cycle, when staging is needed again** (e.g. to validate an infra change before it reaches production): flip `STAGING_INFRA_ENABLED` to `true`, land or manually `workflow_dispatch` the `terraform/**` change, uncomment `deploy-staging.yml`'s `push` trigger and remove its `if: false` guard, validate, then reverse both once done — see `docs/terraform-digitalocean-setup.md`'s "Toggling staging infra on/off" section for the full mechanics.
