# Production Readiness Checklist

Tracks what's left to take `comprobify-web` from staging-only to a live `APP_ENV=production` deployment. Not a replacement for `docs/deployment.md`'s "Production status"/"Production checklist" sections or `docs/terraform-digitalocean-setup.md`'s "What's intentionally still manual" — this is the top-level tracker; those have the actual step-by-step mechanics. Mirrors the equivalent doc in the Comprobify API repo (`../comprobify/docs/production-readiness-checklist.md`), whose production is already live — several items below exist only because that side went first.

Items are grouped by whether they're currently blocked, and on what.

## Security & CI hardening

The Comprobify API repo ran a first holistic security audit (`../comprobify/docs/security-audit-2026-09-12.md`, PR #213) across CI/CD, deployment infrastructure, and application code. This app never had an equivalent pass — the items below are what a parallel check surfaced here, grouped by whether they were fixed as part of that check or are still open. Several are mechanical fixes mirroring the API repo's own resolutions exactly; a few are genuinely different because this repo's situation differs (private vs. public repo, real vs. clean `npm audit` findings, no existing test suite).

**Fixed:**

- [x] **`scripts/rotate-encryption-key.js` no longer accepts `OLD_ENCRYPTION_KEY`/`NEW_ENCRYPTION_KEY` as env vars or CLI args.** This is the incident-response tool for a suspected key compromise — the old version took both keys via `docker compose exec -e KEY=value`, landing them in shell history and the droplet's process list, on the exact droplet an attacker with residual access might be watching. Now prompts interactively with hidden input, fails fast if stdin isn't a real TTY. `docs/guides/encryption-key-rotation.md` updated to the `docker compose exec -it` invocation this requires. Mirrors the identical fix in the API repo (its finding #3)
- [x] **Third-party GitHub Actions pinned to commit SHAs, not mutable version tags** — `appleboy/scp-action`, `appleboy/ssh-action` (both handle `INFRA_SSH_PRIVATE_KEY` and write the droplet's entire `.env`), and `hashicorp/setup-terraform` (runs inside jobs holding `DO_TOKEN`/`CLOUDFLARE_TOKEN`) across `deploy-staging.yml`, `deploy-production.yml`, and all 4 `terraform.yml` job steps. A compromised maintainer account re-pointing a tag could otherwise exfiltrate every secret with no diff in this repo to catch it in review. Mirrors the API repo's finding #4
- [x] **Docker base images pinned by digest, not mutable tags** — `node:24-slim` (all three `Dockerfile` stages) and `caddy:2-alpine` (`deploy/docker-compose.yml`), resolved via `docker buildx imagetools inspect`. A tag can be rebuilt upstream with different contents at any time, silently changing what ships between builds with nothing in this repo's diffs to catch it. Mirrors the API repo's finding #5 (this app has no Redis/worker, so only these two images apply, vs. the API's three)
- [x] **Both deploy workflows scan the built image with Trivy** (`aquasecurity/trivy-action`, SHA-pinned) between `docker build` and `docker push`. **Deliberately informational only for now** (`exit-code: '0'`) — the current base image baseline hasn't been triaged yet (see the open item below), and making it block immediately would red-X the first real deploy for findings nobody's reviewed
- [x] **New `.github/workflows/ci.yml`** runs `npm run type-check` and `npm audit --omit=dev --audit-level=high` on every PR/push to `main`. This repo has no test suite to run (`package.json` has no `test` script — see `docs/guides/encryption-key-rotation.md`'s note on the same gap), so type-checking is the closest available correctness gate, not a unit suite the way the API repo's `ci.yml` runs one. **The audit step uses `continue-on-error: true`, not a hard failure** — unlike the API repo, a real run here found active HIGH/CRITICAL findings in production dependencies themselves (see below), not just a dev-only build toolchain; making it blocking today would red-X every PR immediately
- [x] **New `.github/dependabot.yml`** — npm (grouped weekly PRs; `next`, `next-auth`, `@auth/core`, `prisma`/`@prisma/*` excluded from the group, both because they're load-bearing and because they're currently carrying real findings that need individual review) and github-actions (keeps the SHA-pinned actions current; `appleboy/*` excluded from the group since a behavior change there wouldn't surface until a real deploy runs)
- [x] **GitHub Environment protection rules added to both `staging-infra` and `production-infra`** — required-reviewer rule (`pandc19`, `can_admins_bypass: false`), live-verified via `gh api`. Getting there required making `novaej/comprobify-web` **public** (same GitHub Team billing-plan quirk the API repo hit); a full git-history secret scan was run before accepting that — clean, see the `production-infra` item above for what was checked

**Open — needs a decision or real work, not just a config flip:**

- [ ] **`npm audit --omit=dev --audit-level=high` currently finds 24 vulnerabilities (2 low, 8 moderate, 11 high, 3 critical) in production dependencies**, including **critical-severity findings in `next` itself, `next-auth`, and `@auth/core`** — this is materially different from the API repo's equivalent check, which came back clean. `next` is pinned to an exact version (`16.2.4`, no `^`/`~`) with a non-breaking fix available (`16.3.5`, same major); `next-auth`/`@auth/core` also have fixes available. A plain `npm audit fix` (no `--force`) was tested and pulls in a much larger, unrelated dependency churn (Prisma CLI's own bundled visualization tooling — `d3-*`, `@visx/*`, `elkjs` — none of which this app uses directly) rather than a clean, scoped bump, so it should **not** be run blindly. Triage each finding individually — likely starting with a deliberate, isolated `next`/`next-auth`/`@auth/core` version bump and a real `npm run type-check` + manual smoke test, not a global `audit fix` — before flipping the CI step from `continue-on-error: true` to blocking
- [ ] **Repo-level security settings are all still disabled**, live-verified (`gh api repos/novaej/comprobify-web` → `security_and_analysis`): `dependabot_security_updates`, `secret_scanning`, `secret_scanning_push_protection`, `code_security` all `"disabled"` — unchanged by the visibility flip to public, GitHub doesn't auto-enable these just because a repo goes public. `dependabot_security_updates` is free regardless of visibility and safe to enable unilaterally. `secret_scanning`/`secret_scanning_push_protection` are now free to enable too, since the repo is public — no longer blocked on the private/public decision the way this item originally was
- [ ] **Trivy's `node:24-slim`/`caddy:2-alpine` baseline needs the same triage the API repo did for its `node:20-slim`/`caddy:2-alpine`** (its findings #5 resolution: mostly unfixed-upstream OS package CVEs and Go-stdlib CVEs in the Caddy binary, nothing actionable on the API repo's side) — re-run `trivy image --severity HIGH,CRITICAL` against this app's actual pinned digests once the first deploy workflow run produces a real scan result, and decide whether to flip `exit-code` to `'1'` or add a `.trivyignore`
- [ ] **`docker login` token exposure via process list** (low priority, matches the API repo's still-open findings #9/#12) — `echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io ... --password-stdin` places the ephemeral, narrowly-scoped token as a literal argument to `echo` for an instant, visible via `ps` on the droplet host during that window; the token also lands (base64, not encrypted) in the deploy user's `~/.docker/config.json` after login. GitHub's own log masking prevents it reaching the Actions log either way. Neither the API repo nor this app has fixed this — tracked here for parity, not urgency
- [ ] **A dedicated secrets manager is likely not yet warranted, matching the API repo's own reasoning** (its finding #17) — this app's secrets already live access-controlled and encrypted at rest (GitHub Environment Secrets/Variables), written fresh into the droplet's `chmod 600` `.env` on every deploy, never committed. Revisit once any of: multiple `web` instances need consistent secret distribution, the team grows past one operator, automated rotation becomes necessary beyond `scripts/rotate-encryption-key.js`'s manual path, or a compliance posture (PCI-adjacent given Payphone card payments flow through this app's checkout UX) requires a finer-grained access audit trail than GitHub Environments provide
- [ ] **A holistic application-code security pass (tenant-isolation, XSS, the three-layer permission pattern) hasn't been done for this repo specifically** — everything above is CI/CD and deployment-infrastructure hardening, mirroring what the API repo found on its own equivalent surface. The API repo's application-code findings (an RLS bypass, markdown-injection defense-in-depth, an unescaped email template) don't transfer directly since this app has a different architecture (no Postgres RLS — tenant isolation is enforced at the application layer via `tenantId`-scoped Prisma queries, see CLAUDE.md's "Client management"/"Product catalog" sections) — a dedicated pass over this app's own tenant-scoping code, markdown/HTML rendering (if any), and permission-check call sites is still worth doing before real tenant data flows through it, not assumed clean by analogy
