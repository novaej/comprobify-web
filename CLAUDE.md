## Project Overview

**Comprobify Web** — Next.js 16 (App Router) frontend for the Comprobify electronic invoice API. Allows non-technical users to create, send, and authorize Ecuadorian electronic invoices (facturas electrónicas) from a browser without touching the API directly.

The frontend calls the Comprobify REST API over HTTP. It is **not** a standalone backend — it is a UI layer (BFF pattern).

**Related repo:** `comprobify` (the API) at `../comprobify/`

## CRITICAL RULES

1. **Never import `src/lib/api.ts` in client components** — it is `server-only`. Use `requireContext()` from `src/lib/context.ts` to get the `ApiCtx` in Server Components and Server Actions. Importing it in a client component will throw at build time.
2. **Never expose the user's Comprobify API key to the browser** — it lives only in the `TenantApiKey` table (encrypted), decrypted inside `requireContext()`, and never stored in the JWT or session. Do not pass it through props or return it from Server Actions.
3. **Import `Link`, `redirect`, `usePathname`, `useRouter` from `@/i18n/navigation`** — not from `next/navigation`. The i18n navigation helpers preserve locale context.
4. **All user-visible strings go in `messages/es.json` and `messages/en.json`** — no hardcoded Spanish or English strings in components. Use `useTranslations` (client) or `getTranslations` (server).
5. **`setRequestLocale(locale)` must be called at the top of every async page/layout** — required for static rendering with next-intl. Missing it causes hydration errors in production.
6. **`globals.css` is imported only in `src/app/layout.tsx`** — importing it again in a locale layout causes duplicate style injection.
7. **shadcn components in `src/components/ui/` are never edited manually** — re-run `npx shadcn@latest add` to update them. Put customisations in wrapper components.
8. **Client components must have `'use client'` at the top** — hooks (`useTranslations`, `usePathname`, `useState`) require it. Server Components must not have it.
9. **Server Actions must have `'use server'` at the top** — mutation functions called from forms or buttons.
10. **Keep TanStack Query only for polling** — page-level data fetching uses Server Components (no `useQuery` for initial load). See ADR-005.
11. **All UI changes must be mobile-responsive** — use Tailwind responsive prefixes (`sm:`, `md:`) throughout. Stack layouts on mobile (`flex-col`, single-column grids) and expand on larger screens. Wrap every `<Table>` in `<div className="overflow-x-auto">`. Do not hardcode widths that would overflow on small screens.

## Key Patterns

**Two kinds of ID — local vs. API, both UUIDs:** Every primary key in `prisma/schema.prisma` is a `String @id @default(uuid(7)) @db.Uuid`, as is every foreign key pointing at one. The Comprobify API is *also* UUID-keyed throughout, so the four mirror columns holding its ids — `Tenant.apiTenantId`, `TenantApiKey.apiKeyId`, `Issuer.apiIssuerId`, `Notification.issuerId` — are `@db.Uuid` too, holding the API's value verbatim. **Nothing in this codebase should ever call `Number()` on an id.** The critical consequence: local ids and API ids are the same type, so the compiler cannot distinguish them — passing a local `Issuer.id` where an `ApiCtx.issuerId` belongs compiles fine and fails at runtime (or worse, silently matches nothing). The rule to hold in your head: anything passed to `src/lib/api.ts` or `src/lib/admin-api.ts` is an **API** id; anything in a `db.*` where-clause is a **local** id. `Context.issuer` deliberately carries both (`id` local, `apiIssuerId` API-side), so check which one a call site wants. Route params holding a local id must pass `isUuid()` (`src/lib/utils.ts`) before reaching Prisma, or a malformed segment throws a validation error on the `uuid` column instead of rendering the 404 boundary. Local ids are generated in the app by Prisma — the columns have no `DEFAULT`, so any writer bypassing Prisma must supply one. See `docs/adr/007-uuid-primary-keys.md`.

**BFF (Backend-for-Frontend):** `src/lib/api.ts` is the only place that calls the Comprobify API. All its functions accept `ApiCtx { apiKey: string; issuerId?: number }` as the first parameter. Call `requireContext()` from `src/lib/context.ts` to obtain it — this loads the tenant, issuer, permissions, and decrypted API key in one shot. See `docs/adr/002-bff-pattern.md`.

**Auth (multi-tenant):** Auth.js v5 (next-auth@beta) with a JWT session trimmed to `{ id, email }` only. Tenant, issuer, role, and permissions are resolved on every server request by `requireContext()`, which: (1) verifies the session, (2) loads the `User` → `Tenant` chain from DB, (3) resolves the active issuer from the signed `comprobify_ctx` cookie, (4) decrypts the active `TenantApiKey`. Use `requirePermission(code)` to gate by permission and `hasContextPermission(code)` for conditional Server Component rendering.

**Permission enforcement (three-layer pattern):** Every protected resource enforces permissions at three independent layers: (1) **Page** — `requirePermission('x.y')` at the top of the Server Component; unauthorized roles see "Página no encontrada" (`notFound()`). (2) **Server Action** — `requirePermission('x.y')` at the top of every mutation; this is the real security boundary because actions are POST endpoints that can be called without visiting the page. (3) **UI hiding** — `ctx.permissions.has('x.y')` in the Server Component to suppress buttons/links the user can't act on, passed as props (`canCreate`, `canManage`) into Client Components that render those controls. The three layers are additive and independent: skipping any one creates a gap. `requirePermission` is in `src/lib/context.ts` and shares the overload signature of `requireContext` (supports `{ skipIssuer: true }` for actions that don't need an active issuer). Non-admin users with no issuer assignments are redirected to `/no-issuer-assigned` — not `/settings`, which gives no actionable guidance.

**Tenant onboarding:** New users (no `tenantId`) are redirected to `/onboarding/tenant`, which offers two tabs (`OnboardingTabs`). **Create new company** — `bootstrapTenantAction` calls `registerTenant()` from `src/lib/public-api.ts` (→ `POST /v1/register`), then creates `Tenant` + `TenantApiKey` + `Issuer` + updates `User.tenantId` and `User.role='Owner'` in a single DB transaction, and sets the `comprobify_ctx` issuer cookie. **`POST /v1/register` is new-accounts-only** — it always rejects an already-registered email with `409 CONFLICT` (no more implicit "recovery on re-register" behavior); see "Account recovery" below for the dedicated replacement. **Link existing API account** — for users who already registered directly via the Comprobify API: `linkExistingTenantAction` takes a pasted API key, calls `getCurrentTenant()` (`GET /v1/tenants/me`) and `listTenantIssuers()` (`GET /v1/issuers`) to resolve identity, then mints a *fresh* dedicated key via `createTenantApiKey()` (`POST /v1/keys`) — the pasted key is never stored, only used in-memory to authenticate the linking calls. `Tenant.apiTenantId` is `@unique`, so a given API tenant can only be linked once; a second attempt returns `TENANT_ALREADY_LINKED`. The first user to link becomes `Owner`; everyone else joins via the existing invite flow (`inviteUserAction` in `/users`). Both actions share `registerWebhookBestEffort()` for the non-fatal webhook auto-registration tail. **`createTenantApiKey()`'s `POST /v1/keys` call requires the tenant's `status` to be `ACTIVE`** (`../comprobify/src/services/api-key.service.js`'s `createKey()`) — a pasted key for a tenant that registered but never verified its email fails with `EMAIL_VERIFICATION_REQUIRED` even though `getCurrentTenant()`/`listTenantIssuers()` (Bearer-auth-only, no status check) already succeeded moments earlier. Since no local `Tenant` row exists yet at that point, `resendVerificationAction` (which resolves the tenant via `requireContext()`) can't be reused — `linkExistingTenantAction` instead surfaces `tenantInfo.email` (already fetched) alongside the error code, and `LinkExistingAccountForm` offers a resend button that calls the new `resendVerificationForLinkingAction(email)`, a thin session-gated wrapper around the public `resendVerificationEmail()` call keyed by email instead of by session tenant.

**Account recovery:** `/recover-account` (public, unauthenticated, no session read anywhere in the flow) regains a lost Comprobify API key via `POST /v1/recover` — `recoverAccount()` in `src/lib/public-api.ts`, wrapped by `recoverAccountAction()` in `src/app/actions/recovery.ts`. The endpoint is deliberately anti-enumeration: an unregistered email, an account with no issuer, and a mismatched P12 certificate all return the identical generic `{ ok: true, message }` response, so `recoverAccount()`'s return type distinguishes "matched" from "generic" purely by whether `apiKey`/`tenant`/`issuer`/`environment` are present — never by HTTP status (both cases are `200`). Only a certificate that actually matches the one on file — the same ownership bar fresh registration accepts — gets an observable result: the API revokes whatever key(s) it had for the tenant's **actual current environment** (sandbox or production, resolved server-side from `tenant.sandbox`) and issues a new one. On a real match, `recoverAccountAction` branches on whether the recovered `apiTenantId` already has a local `Tenant` row: if it does, the app's own stored `TenantApiKey` is now stale (the API just revoked it), so the action revokes the local row(s) for that environment and persists the freshly recovered key — resolving its API-side id via a follow-up `listTenantApiKeys()` call, since `POST /v1/recover` only returns the plaintext token (same limitation as `POST /v1/keys`, Common Mistake #18). If no local `Tenant` row exists yet, the action deliberately does **not** create one — doing so would make `linkExistingTenantAction`'s `apiTenantId` uniqueness check treat it as already linked and block the real linking step — instead it hands the recovered key back to the user (copy-once display, same UI as `api-key-manager.tsx`) with instructions to log in and use the existing "Link existing account" tab on `/onboarding/tenant`.

**Issuer provisioning (branch vs. issue point):** First issuer created during onboarding. SRI distinguishes "establecimiento" (branch) from "punto de emisión" (issue point, a POS terminal under a branch), but the API models both through the same `POST /v1/issuers` call — a new `branchCode` counts as a new branch (tier-limited by `maxBranches`), reusing an existing `branchCode` with a new `issuePointCode` counts as a new issue point under it (`maxIssuePointsPerBranch`). `createBranchAction` (`src/app/actions/issuers.ts`) exposes both via the "Nuevo emisor" dialog (`create-issuer-dialog.tsx`) on `/issuers` — a mode toggle picks branch vs. issue point, and for issue-point mode a `Select` of the tenant's existing branch codes supplies `sourceLocalIssuerId`, resolved server-side to that issuer's `apiIssuerId` and sent as `sourceIssuerId`. **`sourceIssuerId` is always sent, even when uploading a fresh P12** — `../comprobify/src/controllers/issuer.controller.js`'s `createBranch` controller only resolves a `sourceIssuer` when no cert file is present, but `issuerService.createBranch` unconditionally reads `sourceIssuer.ruc`/`business_name`/etc. for the new row; omitting `sourceIssuerId` while uploading a cert would crash. The API always inherits `ruc`/`businessName`/`tradeName`/`mainAddress`/cert data from the source issuer regardless of what's posted — `createBranchAction` writes the *API's returned* `apiIssuer.businessName`/`tradeName`/`branchAddress` to the local `Issuer` row, not form input, so the local copy can't silently diverge from what the API actually stored. Promoting to production calls `promoteTenantAction` (Owner-only) → `POST /api/tenants/promote`, which revokes all sandbox `TenantApiKey` rows and inserts new production keys.

**Issuer editing, soft-delete/reactivate, and sequential correction:** `/issuers` is a list with per-card "Editar" (linking to `/issuers/:id`) and an Active/Inactive `Switch` (optimistic, reverts on error — same pattern as `notification-preferences.tsx`). Editable fields are split by what the API actually allows: `businessName`/`mainAddress`/`ruc` are permanently tied to the RUC's SRI registration and have **no** update endpoint anywhere — never expose them as editable. `tradeName`/`branchAddress` *are* independently-stored columns with a real endpoint, `PATCH /v1/issuers/:id` (`updateIssuer()`/`updateIssuerAction`), edited on `/issuers/:id` (`issuer-edit-form.tsx`) alongside the existing logo (`PATCH /v1/issuers/:id/logo`) and certificate (`PATCH /v1/issuers/:id/certificate`) dialogs — both moved here from the old per-card layout. Cert expiry/fingerprint badge (`cert-info.tsx`, shared between the list and edit page) comes from `listTenantIssuers()` (tenant-wide `GET /v1/issuers`) matched to the local row by `String(issuer.apiIssuerId) === apiIssuer.id`; thresholds (>30d ok, 8–30d warning, ≤7d/expired critical) mirror `comprobify/src/services/notification.service.js`'s `CERT_WARN_DAYS`/`CERT_ERROR_DAYS`. **Soft-delete** (`DELETE /v1/issuers/:id` → `removeIssuerAction`) is API-guarded against removing the tenant's last active issuer or one that has ever issued a document (`LAST_ISSUER_CANNOT_BE_REMOVED`/`ISSUER_HAS_DOCUMENTS`) — the latter guard is what keeps this safe at all, since `ride.service.js`/`email.service.js` resolve a document's issuer via the same `active=true`-filtered `findById()` used everywhere else; a deactivated issuer with documents would otherwise break PDF/email for them. **Reactivation** (`PATCH /v1/issuers/:id/activate` → `activateIssuerAction`) re-runs the identical branch/issue-point tier-limit check as creation, so deactivate-then-reactivate can't bypass a plan's caps. The local `Issuer.active` column mirrors this; every query resolving a tenant's issuers (`context.ts`'s `getAccessibleIssuers`/ownership check, the locale layout, `/issuer/select`, `/settings`, `/users`, `postLoginRedirect`'s `_count.issuers`, tenant promotion's sequential seeding) filters on it **except** `/issuers` itself, which intentionally shows both states (inactive rows greyed out) so the toggle has something to act on. **Sequentials**: `GET`/`PATCH /v1/issuers/:id/sequentials[/:documentType]` (`getIssuerSequentials`/`setIssuerSequential`) let Owner/Admin correct the next number per document type — e.g. after migrating from another invoicing system. Sandbox and production counters are tracked in separate schema tables and are edited independently; the edit page only enables the pencil for whichever environment matches `tenant.environment` (editing the dormant one wouldn't affect any real document), and the API itself rejects a `nextSequential` that doesn't exceed the counter's current value (`SEQUENTIAL_CANNOT_DECREASE`) under a `FOR UPDATE` lock, so this can't race a concurrent `POST /v1/documents` into issuing a duplicate sequential.

**Back navigation:** Sub-pages render a "‹ Parent" link via `PageHeader`'s `backHref`/`backLabel` props (or the same `ChevronLeft` + muted-`Link` snippet inline, for pages with a custom header like `invoices/[key]`). Pages with exactly one possible parent hardcode `backHref`/`backLabel`. Pages reachable from **multiple** parent screens (`/invoices/new`, `/invoices/[key]` — linkable from Panel, Comprobantes, and per-type document lists) instead read a `?from=<key>` query param, resolved against the `BACK_TARGETS` allowlist in `src/lib/back-targets.ts`, and every entry-point link must append the matching `from` value (see `DocumentTable`'s `from` prop and the `createHref` links in `documents/page.tsx` / `documents/[type]/page.tsx`). **Adding a new multi-entry sub-page means registering it in `BACK_TARGETS` and updating each entry-point link by hand — this does not happen automatically.** Locale-switching (`UserMenu.handleLocaleChange` in `nav.tsx`) must preserve `useSearchParams().toString()` when calling `router.replace`, or the `from` param (and any other query state) is silently dropped and the back link resets to its default.

`from` must also survive a **Server Action redirect after a mutation**, not just client-side navigation — `createInvoiceAction`/`rebuildInvoiceAction` (`src/app/actions/invoice.ts`) take a `from?: BackTargetKey` parameter purely to append `?from=` onto their post-submit `redirect()` target. Without it, landing back on `/invoices/:accessKey` after creating/rebuilding always fell back to `dashboard` regardless of where the user actually started (e.g. a per-type document list), because the redirect target carried no query string at all. The value is the SAME validated `backTargetKey` the page already computes for its own back-link — `invoices/new/page.tsx` just forwards it into `InvoiceForm`, which forwards it into the Server Action. For the rebuild loop specifically it chains one step further back: Invoice Detail reads its own `from`, appends it to the "Corregir" link (`?rebuild=...&from=...`), and the rebuild form re-forwards that same value — so `?from=` survives the full Invoice Detail → rebuild form → Invoice Detail round trip.

**Localization:** Every visible string goes through next-intl. Add keys to `messages/es.json` first, then mirror in `messages/en.json`. Map API `code` fields (e.g. `DOCUMENT_NOT_FOUND`) to user messages via the `apiError` namespace. See `docs/adr/006-next-intl-localization.md`.

**Status polling:** When a document is in `RECEIVED` status, the Invoice Detail page polls `GET /api/documents/:key/status` (a Next.js proxy route) every 5 seconds using TanStack Query. The proxy forwards to the Comprobify API server-side. Polling stops when status changes or after 2 minutes. See `docs/adr/005-tanstack-query-polling.md`.

**API wake-up ping on login:** The Comprobify API runs on a free-tier instance that spins down after a period of inactivity, so `postLoginRedirect()` (`src/app/actions/auth.ts`, shared by `loginAction` and `completeRegistrationAction`) calls `pingApiHealth()` (`src/lib/api.ts` → unauthenticated `GET /health`, mounted before the `/v1` router in `server.js` — no `ApiCtx`/Bearer token needed) wrapped in Next's `after()` so it runs post-response and never blocks the login redirect. Errors and slow cold starts are swallowed inside `pingApiHealth()` itself — it's a best-effort wake-up call, not a health check anything depends on. `registerAction` does not call this: a brand-new tenant has no API activity to warm up for until onboarding actually calls the API.

**Events timeline on Invoice Detail:** `GET /v1/documents/:key/events` returns raw `{ eventType, fromStatus, toStatus, detail }` rows — rendering `eventType` and a generic `detail` fallback (old behavior) produced unhelpful rows like "Estado actualizado" with no indication of *what* the status became. `describeDocumentEvent()` (`src/lib/event-description.ts`) maps each known `eventType` to a specific, human-readable title plus an optional `detail` string and an optional `{ from, to }` status transition, verified against every `documentEventModel.create()` call site in `../comprobify/src/services/` (`document-creation`, `document-rebuild`, `document-transmission`, `document-email`, `mailgun-webhook`) for the exact `detail` shape each one logs — e.g. `STATUS_CHANGED` → `AUTHORIZED` shows "Autorizado por el SRI" with the authorization number (copyable, via the same `AccessKeyCopy` component used for the access key) instead of a bare status code; `STATUS_CHANGED` → `NOT_AUTHORIZED` shows "No autorizado por el SRI" with the raw `sriStatus` code, since the API has no endpoint exposing SRI's actual rejection message text (it's stored in a `sri_responses` table that's never surfaced — a possible future addition, out of scope for the frontend alone). `invoices/[key]/page.tsx`'s events table has dedicated "Estado anterior"/"Estado nuevo" columns rendering each side of the transition as its own `StatusBadge` (with an `ArrowRight` icon column between them), rather than stacking both badges under the event title — this is also why that table's wrapper was changed from `overflow-hidden` to `overflow-x-auto` (rule 11; six columns can overflow narrow screens). Unknown future `eventType` values still fall back to the `invoiceDetail.eventTypes` namespace (or the raw string), matching the project's general "degrade gracefully on unmapped values" pattern.

**Dashboard summary cards:** `/dashboard` renders three KPI cards (issued this month by type, net authorized revenue this month, all-time needs-attention count) sourced from a single `getDocumentStats()` call (`GET /v1/documents/stats`) rather than computing them from the document list client-side. Net revenue is `FAC + LIQ + DEB − CRE` of each type's `authorizedTotal`; `RET`/`REM` are excluded (no monetary meaning for the dashboard widget). The recent-documents table below the cards is capped to 10 rows (`listDocuments(apiCtx, { limit: 10 })`) with a "Ver todos" link to `/documents` — it is intentionally a preview, not a paginated list, so it has no pager.

**Document list pagination:** `/documents/[type]` (e.g. `/documents/01`) is the canonical full list for a document type and does paginate, via the generic `<DocumentPagination>` component (`src/components/document-pagination.tsx`) reading/writing a `?page=` query param. The Comprobify API's `GET /v1/documents` only returns `pagination: { total, page, limit }` — **no `totalPages` field exists in the response.** Derive it with the exported `getTotalPages({ total, limit })` helper (`Math.ceil(total / limit)`, floored at 1) rather than expecting the API to provide it. See Common Mistake #25.

**`DocumentTable` is shared by two screens:** `/documents/[type]` and the dashboard's recent-documents preview both render `src/components/document-table.tsx` — there is no per-screen copy. Its `labels` prop is a single object with no optional fields beyond `emptyFiltered`/`actions`, so adding a column (e.g. the "Acciones" PDF/XML download buttons, gated on `doc.status === 'AUTHORIZED'`) requires updating **both** call sites' `labels={{ ... }}` construction in `documents/[type]/page.tsx` and `dashboard/page.tsx` — TypeScript will error on a missing required label key at either site, which is the intended guardrail against shipping a half-updated table.

**Sandbox mode:** The `environment` column on the `tenants` table (`'sandbox'` | `'production'`) drives the yellow `SandboxBanner` and the environment badge in Settings. It starts as `'sandbox'` and is flipped to `'production'` once on promotion. There is no `COMPROBIFY_SANDBOX` env var — sandbox state is per-tenant, not global.

**Subscription & billing:** `/pricing` is a Server Component that calls `listTiers()` (`src/lib/public-api.ts` → public `GET /v1/tiers`, no auth) instead of hardcoding plan copy — `pricing-plans.tsx` (Client Component) renders the monthly/yearly toggle and per-tier feature bullets from that response, so quota/price numbers can never drift from `comprobify`'s `subscription-tiers.js`. Picking a paid tier there links to `/register?tier=X&interval=Y`; since actual promotion can happen long after registration, the choice is **persisted on the `Tenant` row** (`intendedTier`/`intendedBillingInterval`, validated end-to-end by `parseIntendedPlan()` in `src/lib/subscription-tiers.ts`) rather than carried as a transient query param — threaded through `registerAction`'s redirect → `/onboarding/tenant?tier=...` → hidden fields in `IssuerSetupForm` → `bootstrapTenantAction`'s `tx.tenant.create()`. `ProductionPromotion`'s confirm step pre-fills a tier `Select` from that stored value (editable before confirming) and calls `promoteTenantAction(initialSequentials, tier?, billingInterval?)` → `promoteTenant()` (`POST /v1/tenants/promote`).

A tenant can also start paying **before** promoting at all — `POST /v1/subscriptions` (`createSubscription()`/`createSubscriptionAction`) works in sandbox, since the manual proof/review pipeline doesn't depend on environment. When this happens, `promote()` on the API side detects the already-`ACTIVE` subscription and ignores any `tier`/`billingInterval` passed to it — `settings/page.tsx` mirrors this by fetching `getMySubscriptions()` and, if one is `ACTIVE`, passing `activeSubscriptionTier` into `ProductionPromotion`, which then skips the tier picker entirely and just links to `/settings/billing` instead (selecting a different tier there would be a silent no-op).

`/settings/billing` (`billing-manager.tsx`) is the single home for the rest of the lifecycle, gated on `billing.read` (view) / `billing.manage` (mutate — proof upload, subscribe, change tier; `tenant.promote` stays separately Owner-only for the actual sandbox→production flip): a current-plan card (tier/quota usage from `getCurrentTenant()`), a `SubscribeCard` when no subscription is in flight (`subscriptions.every(s => s.status === 'CANCELLED' || s.status === 'EXPIRED')`, mirroring the API's own `findActiveOrPendingByTenantId` exclusion), a `ChangeTierCard` when one is `ACTIVE` (upgrades apply immediately prorated; downgrades schedule for `current_period_end` via `pending_tier` — see `changeTier()` → `POST /v1/subscriptions/change-tier`), a pending-payment card with bank-transfer details + file upload when a payment needs proof, and a full subscription/payment history (`ApiSubscriptionInfo.status` covers the full `PENDING_PAYMENT | PAYMENT_RECEIVED | INVOICE_PROCESSING | ACTIVE | EXPIRED | SUSPENDED | CANCELLED` set per the API's `chk_subscriptions_status` constraint, not just the four happy-path values). **`bankTransfer` is only ever returned once**, from whichever call started a payment (`promoteTenant`/`createSubscription`/`changeTier`) — there is no endpoint to re-fetch it — so all three Server Actions cache it onto `Tenant.pendingBankTransfer` (a Json column). Because the bank details are static config (`config.bankTransfer` on the API, identical for every tenant and every payment), `/settings/billing/page.tsx` keeps the cached copy **indefinitely** rather than clearing it after each payment verifies — a renewal payment in particular is opened by a backend cron job with no frontend call involved, so there is no fresher `bankTransfer` ever returned for it, and clearing the cache after the first payment would leave every later renewal with nothing to show.

**Recurring renewals:** A renewal reuses the exact same proof/review/link-invoice pipeline as the initial subscription — a new `payments` row with `purpose: 'RENEWAL'` (no `target_tier`) opens automatically ~7 days before `current_period_end`, surfaced to the tenant only via the `SUBSCRIPTION_RENEWAL_DUE` notification/email (see below) and then `GET /v1/subscriptions/me`, never as a Server Action response — so it's the one payment-starting path that can't populate `Tenant.pendingBankTransfer` itself, relying entirely on the indefinite cache above. If it runs unpaid past a grace period, the subscription moves to `EXPIRED` and the tenant is auto-downgraded to FREE (`SUBSCRIPTION_EXPIRED` notification/email). `billing-manager.tsx`'s history list labels a `RENEWAL` payment distinctly from `TIER_CHANGE` (no target tier to show).

**Payment/subscription notifications:** `reviewPayment`/the renewal job now fire real notifications instead of leaving both sides to poll — `PAYMENT_VERIFIED`/`PAYMENT_REJECTED` (on every payment decision, regardless of `purpose`) and `SUBSCRIPTION_RENEWAL_DUE`/`SUBSCRIPTION_EXPIRED` are real `notifications.types` alongside `DOCUMENT_AUTHORIZED`/`CERT_EXPIRING`/`CERT_EXPIRED` (`notification-preferences.tsx`'s `LIVE_TYPES`, not `RESERVED_TYPES`). `getNotificationHref()` (`src/lib/notification-link.ts`) routes all four to `/settings/billing` — none of their metadata fields (`paymentId`/`subscriptionId`/`tier`/`amount`) has a more specific page to deep-link to. Activation itself (the self-billed invoice authorizing) still has no notification of its own — `GET /v1/subscriptions/me` remains the only way to see that happen.

**Error handling:** The Comprobify API returns RFC 7807 Problem Details on all errors. `ApiError` in `src/lib/errors.ts` wraps these. In Server Actions, catch `ApiError` and pass `error.code` to the i18n `apiError` namespace for user-friendly messages.

**Form → Server Action flow:**
1. Client component renders the form (React Hook Form + Zod client-side validation)
2. On submit, calls a Server Action (async function with `'use server'`)
3. Server Action calls `src/lib/api.ts` with the validated payload
4. On success, calls `redirect()` to the Invoice Detail page
5. On `ApiError`, returns `{ error: error.code }` for the client to display

**Catalog fetching:** SRI lookup tables (ID types, payment methods, tax rates) live in the API database and are fetched server-side at page load via `listCatalogIdTypes`, `listCatalogPaymentMethods`, `listCatalogTaxRates` in `src/lib/api.ts`. The page fetches all three in parallel and passes them as props to the Client Component form. This keeps selects in sync with the DB without hardcoding strings in the frontend. The IVA rate options are further filtered client-side by the `IVA_RATE_CODES` constant in `invoice-form.tsx` to exclude historical rates.

**Client management:** Clients are saved in the app's own `clients` table (Prisma), scoped per **tenant** (shared by all users in the same org). The CRUD screen is at `/clients`. On the invoice creation page, the tenant's clients are fetched server-side and passed as `catalogs.clients`. A search icon button next to the buyer ID field does an exact `idNumber` lookup and fills name, email, address, and ID type when a match is found. Every DB operation uses `updateMany`/`deleteMany` scoped to `tenantId` so one tenant can never touch another's records.

**Product catalog:** Products are saved in the app's own `products` table (Prisma), scoped per **tenant**. The catalog page (`/catalog`) provides full CRUD via `src/app/actions/catalog.ts`. On the invoice creation page, all tenant products are fetched server-side alongside the SRI catalogs and passed to `InvoiceForm` as `catalogs.products`. The `ProductSearch` combobox in each line-item row filters products client-side as the user types, then fills all item fields on selection. The dropdown is rendered via `createPortal(…, document.body)` with `position: fixed` to escape the `overflow-x-auto` table wrapper. ICE and IVA turismo fields are intentionally excluded — the invoice API does not currently support them.

**Document templates:** Full invoices (buyer, line items, payment methods, additional fields) can be saved as reusable templates via `src/app/actions/templates.ts`, backed by the `DocumentTemplate` Prisma model — scoped per **tenant**, not sent to or read from the Comprobify API. The model's `documentType` column defaults to `'01'` (invoices) but is a real, generic column (`@@unique([tenantId, documentType, name])`) so other SRI document types can reuse the same table once they get a create flow — today only invoices do. `saveInvoiceTemplateAction` runs an `upsert` keyed on `(tenantId, documentType, name)`, so saving under an existing name overwrites it; `InvoiceForm` shows an inline warning when the typed name matches an existing template, and pre-fills that name after a template is loaded so re-saving defaults to "update." The stored `data` JSON is the exact same shape as `InvoiceFormData` (`src/app/actions/invoice.ts`) — `toInvoiceFormData`/`templateToFormValues` in `invoice-form.tsx` convert between that and the form's Zod-validated `InvoiceFormValues` (which use `''` for empty optional fields instead of `undefined`).

**Sign-only vs. sign-and-send on invoice creation:** `InvoiceForm` exposes two submit buttons — "Firmar y Enviar" (primary, also the Enter-key default) and "Firmar" (outline). Both call `form.handleSubmit()` to validate, then open the *same* confirmation `Dialog`, tracked by a `submitIntent: 'sign' | 'signAndSend'` state that switches the dialog's title/description/icon/submit label between the `confirm` and `confirmSignOnly` i18n blocks. `handleConfirmedSubmit` passes `submitIntent === 'signAndSend'` as `createInvoiceAction`'s second argument (`sendAfterSigning: boolean`), which gates the existing best-effort `sendToSri()` call — `false` skips it entirely, leaving the document in `SIGNED` status. A document signed-only is not stuck: the Invoice Detail page already shows a recovery "Enviar" button for any `SIGNED` document (`src/components/invoice-actions.tsx`), so this reuses an existing path rather than adding a new one.

**Rebuild ("Corregir") reuses the create form:** `/invoices/new?rebuild=<accessKey>` is the same route and the same `InvoiceForm`, not a separate screen. `invoices/new/page.tsx` fetches the document, checks `status` is `RETURNED`/`NOT_AUTHORIZED` and `requestPayload` exists (silently falling back to a blank create form on any failure — not found, wrong status, missing payload), and passes `rebuildFrom={{ accessKey, payload: document.requestPayload, issueDate }}` to `InvoiceForm`. `requestPayloadToFormValues()` (the inverse of `buildCreateDocumentPayload()` in `src/app/actions/invoice.ts`) converts that stored body back into `defaultValues` so the form is pre-filled on first render. The exact same dual-button/confirm-dialog mechanism above is reused — `isRebuild = Boolean(rebuildFrom)` just swaps every label/dialog-copy lookup to a `*Rebuild`-suffixed i18n key and routes `handleConfirmedSubmit` to `rebuildInvoiceAction(accessKey, data, sendAfterSigning, from)` instead of `createInvoiceAction`. `rebuildDocument()` → `POST /v1/documents/:key/rebuild` preserves the access key and sequential; only the content and status (back to `SIGNED`) change. Both the top header back-link and the bottom "Volver" button point at `/invoices/:accessKey` (via a `backHref` prop computed once in the page and passed straight through — not re-derived inside `InvoiceForm`) instead of the dashboard/documents hub.

**Credit notes (Nota de Crédito, document type `04`):** A separate create flow from invoices — `POST /v1/documents` is document-type agnostic server-side (dispatches on `body.documentType`), but the request shape differs enough (no `payments`; instead requires `originalDocument: { documentType, number, issueDate }` and `motivo`) that it gets its own `CreditNoteForm` (`src/components/credit-note-form.tsx`) and route (`/credit-notes/new`) rather than reusing `InvoiceForm`. `CreateCreditNotePayload` lives alongside `CreateInvoicePayload` in `src/lib/api.ts` as a discriminated union (`CreateDocumentPayload`); item/tax shape (`mainCode`/`auxCode`, not `auxiliaryCode` as the docs site's example incorrectly shows) is identical to invoices and reuses `InvoiceItem`. `ProductSearch` (the product-catalog autocomplete) was extracted from `invoice-form.tsx` into its own `src/components/product-search.tsx` so both forms share it. There's no SRI endpoint to look up a document by its `NNN-NNN-NNNNNNNNN` number — only by access key — so `originalDocument.number` is always reconstructed server-side as `${issuer.branchCode}-${issuer.issuePointCode}-${document.sequential}` (`getInvoiceForCreditNoteAction`, `src/app/actions/credit-note.ts`), never typed by the user. Two entry points populate the form, both converging on that same action: (1) `/invoices/[key]`'s `InvoiceActions` shows a "Crear nota de crédito" button for `AUTHORIZED` type-`01` documents, linking to `/credit-notes/new?fromInvoice=<accessKey>`, which the page resolves server-side before first render; (2) a "Buscar comprobante" dialog inside `CreditNoteForm` itself (for the documents-hub entry point, with no known source invoice) calls `searchCreditableInvoicesAction` (wraps `listDocuments` filtered to `documentType: '01', status: 'AUTHORIZED'`) then the same `getInvoiceForCreditNoteAction` on selection. Either way the user can still edit every pre-filled field afterward — including replacing items entirely for a credit note that doesn't track specific products (e.g. a flat monetary adjustment with a manual `mainCode`/description and the credited amount as `unitPrice`) — **except buyer identity**, see below. Rebuild (`?rebuild=<accessKey>`) and the sign-only/sign-and-send dual-submit dialog follow the exact same mechanism as invoices (see above), just against `rebuildCreditNoteAction`/`createCreditNoteAction`. `InvoiceActions`' rebuild link is routed per `documentType` via `REBUILD_HREFS` (`src/components/invoice-actions.tsx`) since `/invoices/[key]` is the shared generic detail page for every document type, not just invoices — `DocumentTable` already links every type's rows there.

**No SRI/API lookup exists for documents outside this system, so credit notes can only reference invoices created here.** Checked `../comprobify/src/services/sri.service.js`: SRI only exposes two SOAP operations — `RecepcionComprobantesOffline` (submit) and `AutorizacionComprobantesOffline` (check authorization, which takes only an already-known access key and returns just that document's status — not a search). There is no SRI service, and never could reasonably be one, that looks up a document by buyer ID + date + number (the fields the SRI's own free invoicing tool's "Validar Factura" button uses) — that would let any taxpayer query any other taxpayer's invoice history. `CreditNoteForm`'s "Comprobante a corregir" card shows a `originalDocument.hint` string making this explicit, since it's not obvious why the search is scoped to this tenant's own documents only.

**Credit notes can't exceed the original invoice's remaining (uncredited) balance.** `GET /v1/documents/:key/credit-notes` (`getCreditNotesBalance()` in `src/lib/api.ts`) sums every `AUTHORIZED` credit note already referencing a document (by its stored `originalDocument.number`, scoped to the same issuer) and returns `remaining = originalDocument.total − creditedTotal`. `CreditNoteForm` fetches this whenever an original document is selected (`getInvoiceForCreditNoteAction` already calls it for the prefill paths; the search-select flow gets it from the same action) and disables both submit buttons + shows a destructive warning when the live-computed `totals.total` would exceed it. The same check is re-run **server-side** in `createCreditNoteAction`/`rebuildCreditNoteAction` (`assertWithinRemainingBalance` in `src/app/actions/credit-note.ts`) as defense-in-depth against a stale/bypassed client — it recomputes the grand total from the submitted items rather than trusting a client-sent number. Per the endpoint's own docs, this is "a UI guard, not a hard guarantee" — two credit notes created back-to-back before the first authorizes won't see each other in the sum (no concurrency locking). **Rebuild mode is a partial exception:** a credit note's stored `requestPayload.originalDocument` only has `documentType`/`number`/`issueDate`, not the original's access key, so `resolveOriginalAccessKeyAction` (`src/app/actions/credit-note.ts`) re-derives it via an exact-match `listDocuments` lookup on the embedded sequential; if that resolution is ambiguous or fails, the balance check and display are silently skipped for that rebuild (same graceful-degradation pattern used elsewhere in this flow), not a hard error.

**Credit note buyer identity is locked to the original invoice's buyer once one is selected.** `idType`/`id`/`name` become read-only (`buyerLocked` in `credit-note-form.tsx`) — a credit note must legally apply to the same buyer as the invoice it credits. `address`/`email` stay editable since those are delivery details, not legal identity, and the original invoice's stored email might be outdated.

**PDF preview on Invoice Detail:** For `AUTHORIZED` documents, "Vista previa PDF" is the primary visible action button inside `InvoiceActions` itself (`src/components/invoice-actions.tsx`) — not a separate component below it. There used to be a standalone "Descargar PDF (RIDE)" button *and* a separate preview toggle, which read as two redundant "see the PDF" entry points; they were merged into one: clicking "Vista previa PDF" toggles `previewOpen` state and lazy-mounts `InvoicePdfPreview` (via `invoice-pdf-preview-lazy.tsx`) in a block below the action row, and the actual file download now lives as a small "Descargar" button *inside* the preview panel itself (`invoice-pdf-preview.tsx`) rather than as a top-level action — download is a secondary affordance once you're already looking at the document, not a competing primary button. `invoice-pdf-preview-lazy.tsx` is a tiny Client Component whose sole job is calling `next/dynamic(..., { ssr: false })`: Next.js's Turbopack build rejects `ssr: false` called directly from a Server Component (a hard build error, not just a warning), so the dynamic-import call must live in its own Client Component file, never inline in a page. `InvoicePdfPreview` itself (`react-pdf` + `pdfjs-dist`) points `<Document file={...}>` at the existing `/api/documents/:key/ride` download route — no separate endpoint needed — and uses a `ResizeObserver` on its container to keep the rendered page responsive (rule 11). See Common Mistake #27 for the worker-loading gotcha specific to this library.

**Base UI `SelectValue` display:** `@base-ui/react` Select.Value does not mirror the selected item's children text — it renders the raw `value` string by default. To show a human-readable label, pass a render function as children:
```tsx
<SelectValue>
  {(value: string | null) => catalog.find((x) => x.code === value)?.description ?? value}
</SelectValue>
```

**Marketing site / domain routing:** The `(marketing)` route group under `src/app/[locale]/` holds all public-facing pages (landing `/` and pricing `/pricing`). These render a standalone header+footer layout with no Nav or auth — and stay that way **regardless of auth state**: neither page redirects an authenticated visitor away, so someone can open the landing page in a second tab while logged in and still see the marketing chrome. `src/proxy.ts` enforces domain separation: `MARKETING_HOSTS` (`comprobify.com`, `staging.comprobify.com`) only serve marketing routes and issue 301 redirects to `DOMAIN_PAIR[host]` for anything else; `APP_HOSTS` (`app.comprobify.com`, `app-staging.comprobify.com`) redirect marketing routes to the marketing host. Localhost and unknown hosts bypass hostname routing so local dev works without configuration — which means a marketing path can reach `[locale]/layout.tsx` while authenticated, something the two-domain production setup would normally intercept first. That layout wraps authenticated users in the `Nav`/`TopBar` shell, and a nested layout like `(marketing)/layout.tsx` has no way to opt out of markup its parent already applied — so `proxy.ts` computes `isMarketingPath` unconditionally and forwards it to Server Components as the `x-marketing-route` request header — by mutating `req.headers` directly *before* calling `intlMiddleware(req)`, not by building a second `NextResponse.next({ request: { headers } })` and copying its headers over. next-intl's own middleware forwards the resolved locale to Server Components the exact same way internally (cloning `req.headers` into its own response), so two independently-built responses both setting the special `x-middleware-override-headers`/`x-middleware-request-*` headers would clobber each other via `.set()`; mutating `req.headers` first means next-intl's own clone picks up our header for free, leaving only one such response ever constructed. `[locale]/layout.tsx` reads that header with `headers()` and treats the route as unauthenticated whenever it's set, skipping the Nav wrapper (and the `getLayoutProps` DB call) unconditionally. Only `/login` itself still redirects an already-authenticated session to `/dashboard`. `pricing` is added to `PUBLIC_ROUTES` so unauthenticated users can reach it.

**Marketing landing page:** `(marketing)/page.tsx` is a scroll narrative — hero → "empieza en tres pasos" → supported document types → pricing teaser → FAQ → final CTA. Motion is dependency-free (no `framer-motion`): `src/components/reveal.tsx` is an IntersectionObserver fade/lift wrapper used to stagger sections in, and the hero/final-CTA glows use the `animate-glow-drift` keyframe in `globals.css`. **Every animation lives inside a `@media (prefers-reduced-motion: no-preference)` guard, and `Reveal` additionally carries `motion-reduce:` variants that force the visible state** — a reduced-motion visitor must never end up looking at an `opacity-0` section. `LandingSteps` is the only stateful piece: one 3-step timeline with a tab switcher ("Emitir desde la web" / "Integrar con mi sistema"), where steps 1–2 are shared and only step 3 + the closing CTA differ (register vs. `docs.comprobify.com`). Its rail fills as steps scroll into view, but **step text never depends on the observer** — only colour does — so the section reads correctly if JS never runs.

The supported-document-types strip is **derived from the API, not hardcoded**: `getSupportedDocumentTypes()` in `page.tsx` unions `allowedDocumentTypes` across the public `GET /v1/tiers` catalog (`listTiers()`, no auth). That union equals `SUPPORTED_TYPES` in `../comprobify/src/builders/index.js` by construction — `src/constants/subscription-tiers.js`'s header comment states the field gates against it — so the strip is `01`/`04` today and promotes `05`/`06`/`07` from "coming soon" to supported on its own when their builders ship. The fetch is wrapped in try/catch returning `null`: a cold or down API hides the section rather than breaking the landing page. The remaining codes come from `SRI_DOCUMENT_TYPES` in `landing-doc-types.tsx`, which is the SRI's fixed catalog (safe to hardcode) — *not* a capability list.

Header/nav rules: the marketing header is capped at **three** nav destinations (Cómo empezar → `#como-empezar`, Precios, Documentación) with the footer carrying the full site map in four columns, and has exactly **one filled button** (Crear cuenta) — login is a text link, since two competing auth buttons left no clear primary action. The header is sticky + backdrop-blurred with no JS. `MarketingMobileMenu` exists because the nav links were previously `hidden sm:flex`, leaving phone visitors no header path to Pricing or Docs at all. Anchor targets need `scroll-mt-20` so the sticky header doesn't cover the heading on jump; the `#como-empezar` link is same-page (`href="#como-empezar"`) on the landing page but locale-prefixed (`/${locale}#como-empezar`) in the header and mobile menu, since those also render on `/pricing`.

**Marketing SEO:** Only the `(marketing)` routes are indexable — everything else sits behind auth and has no SEO value. `src/lib/seo.ts` is the single source of truth for three things, shared by `src/app/robots.ts`, `src/app/sitemap.ts`, and every `(marketing)` page's `generateMetadata`: `MARKETING_BASE_URL` (from `NEXT_PUBLIC_MARKETING_URL` — the **marketing** host's own origin, e.g. `https://comprobify.com`; deliberately not `NEXT_PUBLIC_APP_URL`, which points at the app host), `SEO_INDEXABLE` (`true` only when `NEXT_PUBLIC_APP_ENV === 'production'`, reusing the same flag Sentry already uses to tag environments), and `localeAlternates(pathname)` for es/en hreflang. `robots.ts`/`sitemap.ts` emit a blanket `Disallow: /` and an empty sitemap respectively whenever `SEO_INDEXABLE` is false — this keeps the real, publicly-reachable `staging.comprobify.com` domain out of search results entirely, not just unlisted. `(marketing)/layout.tsx` sets `metadataBase` from `MARKETING_BASE_URL` once; the landing and pricing pages each export their own `generateMetadata` reading a `<screen>.seo.{title,description}` i18n key and setting `alternates.canonical`/`alternates.languages`. Adding a new marketing page means: add it to `MARKETING_ROUTES` in both `src/proxy.ts` and `src/lib/seo.ts` (kept as two separate arrays since one drives host routing and the other drives crawl/sitemap — no shared import, so keep them in sync by hand), add a `generateMetadata` export, and add its `seo` i18n keys to both message files.

**Super admin panel:** `/admin` is an internal operator area gated by `User.isSuperAdmin = true`. `requireSuperAdmin()` (`src/lib/admin-context.ts`) checks the session and that flag — any non-super-admin (including normal tenants) is redirected to `/dashboard`. Super admins have no `tenantId`, so `requireContext()` detects `isSuperAdmin` and redirects them to `/admin` rather than `/onboarding/tenant` (the normal no-tenant path). `src/lib/admin-api.ts` is the only call site for `/v1/admin/*` routes; it uses a static `COMPROBIFY_ADMIN_SECRET` Bearer token, never a tenant API key — there is no `ApiCtx` here. All API paths start with `/v1/admin/` (the Comprobify API mounts the admin router at `/v1` → `/admin`). The admin layout uses `AdminNav` (`src/components/admin-nav.tsx`), a sidebar component with the same structure, CSS classes, and mobile hamburger as the main `Nav`. The locale layout's unauthenticated/no-tenant branch renders `<>{children}</>` with no wrapper element — a wrapping `<main>` would break `h-full` height propagation to the admin sidebar (see Common Mistake #36). The admin error boundary (`src/app/[locale]/admin/error.tsx`) links back to `/admin/tenants`, not `/dashboard`, since super admins have no tenant to return to. A seed script (`prisma/seed.js`) creates `support@comprobify.com` as the super admin user — run with `npm run db:seed` after setting `ADMIN_SEED_PASSWORD` in `.env`.

**API key self-service (`/api-keys`):** Owner/Admin (`apikeys.read`/`apikeys.manage`) mint their own Comprobify API keys here for use in Postman, an ERP, or any direct integration — reached from a card on `/settings` (the page previously had no entry point anywhere in the UI). The page shows a copy-once cleartext key plus a usage panel (base URL from `COMPROBIFY_API_URL`, `Authorization: Bearer` header, curl snippet, link to `docs.comprobify.com`); every stored row keeps only the AES-encrypted key and its last four digits.

Two constraints make this safe to expose. **(1) Environment.** `POST /v1/keys` defaults `environment` to `'sandbox'` (`../comprobify/src/services/api-key.service.js` → `createKey`), and the API's `require-matching-environment.js` middleware 401s any key whose environment differs from the tenant's `sandbox` flag (`API_KEY_ENV_MISMATCH`) — it guards `GET /v1/tenants/me` and, via `resolve-issuer.js`, every issuer-scoped route. `createTenantApiKeyAction` must therefore pass `ctx.tenant.environment` explicitly and persist the environment the API *returned*, not the one it asked for. **(2) Which key the app itself uses.** `findAppApiKeyRow()` (`src/lib/tenant-api-key.ts`) is the single resolver shared by `requireContext()` and the `/api-keys` page: oldest active row matching the tenant's environment. It is deterministic on purpose — a bare `findFirst({ isActive: true })` let a newly-minted Postman key silently become the key the web app signs its own requests with. That row is badged "En uso por la app" and its revoke button is disabled, because the API refuses to revoke the key that authenticated the revoke request (`SELF_REVOCATION_FORBIDDEN`) and revoking it would cut the app off from the API entirely; `revokeTenantApiKeyAction` re-checks this server-side.

**Notification system:** Notifications arrive via webhook (`POST /api/webhooks/receive`), are upserted into the local `notifications` table, and surfaced in the sidebar bell. `<NotificationSync />` fires a catch-up on every authenticated page load. The bell auto-refreshes every 60 seconds. `notification.issuerId` stores the **API-side** issuer id (a UUID) — always compare against `Issuer.apiIssuerId`, never `Issuer.id`. Both are UUIDs, so the compiler will not catch a mix-up. Fan-out: Owner/Admin receive all notifications; other roles only receive issuer-scoped ones if they have a matching `UserIssuerAccess` row; tenant-level notifications (`issuerId = null`) go to all active users.

**Webhook receiver HMAC:** The receiver route (`src/app/api/webhooks/receive/route.ts`) must call `request.text()` **before** any `JSON.parse()` to preserve the raw body for signature verification. Calling `request.json()` first consumes the stream and makes the raw body unavailable for HMAC comparison.

**Error monitoring (Sentry):** `@sentry/nextjs` captures unhandled errors across all runtimes. `src/instrumentation.ts` boots the server/edge SDK via Next.js's `register()` hook and wires `onRequestError` so every Server Component, Server Action, and Route Handler crash that **propagates unhandled** is reported automatically. Errors caught and swallowed inside a `try/catch` (to return a friendly `{ error: CODE }` instead of crashing) do **not** get this automatic capture — call `Sentry.captureException(err)` explicitly in those catch blocks, or the failure leaves no trace (see Common Mistake #23). `src/app/global-error.tsx` is the root client-side error boundary — it calls `Sentry.captureException` before showing a recovery UI. `src/app/[locale]/error.tsx` is a second, more specific boundary nested inside the locale layout — it catches crashes from any page/Server Component under `[locale]` (so it still renders inside `NextIntlClientProvider`/`Nav`, unlike `global-error.tsx` which replaces the whole `<html>`) and shows a translated recovery UI with "Retry" and "Back to dashboard". It always renders the generic `apiError.UNKNOWN` message rather than the original `ApiError.code`, because Next.js strips custom `Error` properties (and redacts `message` in production) when forwarding a server-render crash to a client error boundary — see Common Mistake #28. Sentry is **disabled locally** (SDK skips `init` when no DSN is set); set `SENTRY_DSN` + `NEXT_PUBLIC_SENTRY_DSN` in Vercel and tag the env with `APP_ENV=staging` or `APP_ENV=production`. The `org` value in `withSentryConfig()` (`next.config.ts`) must be the organization **slug** (Settings → General Settings), not the numeric ID embedded in the DSN hostname (`o<id>.ingest...`) — using the latter makes every build fail source map upload with `Project not found`.

**Loading skeletons:** `loading.tsx` files are Suspense boundaries Next.js shows automatically (on client navigation and SSR streaming) while a route segment's Server Component fetches data — no props, no i18n, no `'use client'`. Add one **only** where the page does a real external-API fetch with perceptible latency and has a layout stable enough to be worth mirroring; not a blanket pattern for every route (see `docs/guides/coding-guidelines.md → "Adding a new screen" step 4`). `src/app/[locale]/dashboard/loading.tsx` and `src/app/[locale]/invoices/[key]/loading.tsx` are the current examples — each lays out `<Skeleton>` blocks (`src/components/ui/skeleton.tsx`) shaped like the real page (KPI cards + table rows; header + info grid + events table) so there's no layout shift on resolve. Keep a skeleton in sync if its page's layout changes structurally.

**Not found page:** `src/app/[locale]/not-found.tsx` is the locale-aware 404 boundary — nested inside `[locale]/layout.tsx` (same nesting behavior as `error.tsx`, so it still renders with `NextIntlClientProvider`/`Nav`/locale context intact), it handles both genuinely unmatched routes under a valid locale and explicit `notFound()` calls deeper in the tree (e.g. `invoices/[key]/page.tsx` when a document doesn't exist **or** the access key in the URL is malformed — `getDocument()`'s only validated param is `key`, so a 422 `VALIDATION_FAILED` there is treated the same as a 404). New `notFoundPage` i18n namespace. It does **not** cover an invalid `:locale` segment itself — see Common Mistake #29. Its "Volver al panel" recovery link is a plain `<a href={`/${locale}/dashboard`}>` (locale read via `getLocale()` from `next-intl/server`), **not** the `Link` component from `@/i18n/navigation` — see Common Mistake #30.

**Complete registration (invited users):** Auth.js `authorize()` returns `null` for users with no `passwordHash`, so `signIn()` throws `AuthError` — invited users cannot authenticate the normal way. `loginAction` pre-checks `inviteStatus` + `passwordHash` **before** calling `signIn()` and redirects to `/complete-registration` when appropriate. `completeRegistrationAction` validates the invite is still pending, hashes the password, marks the user `ACTIVE`, signs them in, and calls `postLoginRedirect()`. The route is in `PUBLIC_ROUTES` in `src/proxy.ts`.

## Next.js 16 Breaking Changes

This project runs Next.js **16** (not 13-15). Key differences from older versions:

1. **`src/middleware.ts` → `src/proxy.ts`** — the file convention was renamed. The export must be named `proxy` (not `default` or `middleware`). next-intl's `createMiddleware` still works — just rename the file and the export: `export const proxy = createMiddleware(routing)`.

2. **shadcn/ui uses Base UI instead of Radix UI** — components like `Button` no longer have an `asChild` prop. To render a link as a button, apply `buttonVariants()` class to the `<Link>` directly instead of wrapping with `<Button asChild>`.

3. **`params` is a `Promise`** — in Next.js 16, all page/layout params are async: `params: Promise<{ locale: string }>`. Always `await params` before accessing properties.

4. **Read `node_modules/next/dist/docs/`** before using any Next.js API — the docs bundled with the package reflect the actual installed version.

## Common Mistakes to Avoid

1. Using `next/navigation`'s `Link`/`redirect`/`usePathname` instead of `@/i18n/navigation` — breaks locale context and produces wrong URLs.
2. Calling `getTranslations` in a Client Component — use `useTranslations` instead (it reads from the provider).
3. Adding `'use client'` to a page that only needs a small interactive piece — extract only the interactive part into a client component.
4. Forgetting `setRequestLocale(locale)` in a page — causes stale locale in nested server components.
5. Hardcoding currency formatting — always use `Intl.NumberFormat('es-EC', { style: 'currency', currency: 'USD' })`.
6. Adding a new message key to only one locale file — always update both `es.json` and `en.json` together.
7. Using TanStack Query `useQuery` for initial page data — only use it for the polling proxy route.
8. Making fetch calls from client components to the Comprobify API directly — all calls go through server-side code or the proxy route.
9. Leaking the user's Comprobify API key to the browser — it must stay server-side only, decrypted via `requireContext()`. Never pass it as a prop, include it in the session, or return it from a Server Action.
10. Editing `src/components/ui/` files directly — they are auto-generated by shadcn. Use wrapper components.
11. Using `<SelectValue />` with no children when populating options from a catalog — Base UI renders the raw `value` (the code) instead of the label. Always pass a render function: `<SelectValue>{(v) => catalog.find(x => x.code === v)?.description ?? v}</SelectValue>`.
12. Redirecting from a Server Action without calling `revalidatePath('/', 'layout')` first when the action changes layout-visible data (e.g. tenant name, environment, issuer list) — Next.js performs a soft navigation and reuses the cached layout RSC payload, so the Nav and other layout elements appear stale until a manual reload. Always call `revalidatePath('/', 'layout')` before `redirect()` in those actions.
13. Wrapping `redirect()` in a broad `try/catch` without re-throwing `NEXT_REDIRECT` — applies both inside the Server Action itself and in any Client Component that `await`s the action call in its own `try/catch`. `redirect()` works by throwing a special error with `digest` starting with `'NEXT_REDIRECT'`. If a catch block swallows it (e.g. returning `{ error: 'UNEXPECTED_ERROR' }` or calling `setError(...)`), the redirect either never fires, or — as happened in `IssuerSetupForm`/`LinkExistingAccountForm` — a stray error message flashes on screen before the redirect eventually goes through. Re-throw it: `if ((err as { digest?: string }).digest?.startsWith('NEXT_REDIRECT')) throw err;`
14. Rendering an absolutely-positioned dropdown inside an `overflow-x-auto` container — the overflow clips it. Use `createPortal(…, document.body)` with `position: fixed` and coordinates from `getBoundingClientRect()` instead.
15. **Writing `api.ts` interfaces without verifying against the actual API source** — the types are hand-maintained with no code generation. Every time a new function is added or an existing one modified, open `../comprobify/src/controllers/` and trace the exact `res.json(...)` fields, then follow every service/presenter function the controller calls. Writing an interface based on the function name or assumed conventions will produce silent runtime failures (fields come back `undefined`, actions silently do nothing, DB writes fail). See `docs/guides/coding-guidelines.md → "Adding a new API endpoint call"` for the full procedure.
16. **Typing an API `id` as `number`, or calling `Number()` on one** — the Comprobify API is **UUID-keyed throughout**: every table is `id UUID PRIMARY KEY DEFAULT uuid_generate_v7()` (see `../comprobify/db/migrations/001_create_issuers.sql`, `023_create_api_keys.sql`, `035_tenants.sql`, `044_notifications.sql`, `052_subscriptions_and_payments.sql`), and its own routes validate with `param('id').isUUID()`. Type every API id as `string` and never coerce it — `Number("0199a3f2-…")` is `NaN`, which Prisma rejects on write and which surfaces to the user as an opaque internal error. This entry previously claimed the API used `BIGSERIAL` and instructed applying `Number(record.id)` at every Prisma write site; that was wrong, and it silently broke tenant onboarding (`Number(result.tenant.id)` → `NaN` → `DB_WRITE_FAILED`) plus every admin payment/tenant action. The local mirror columns are `@db.Uuid` for this reason.
17. **Using an API field name that differs from the actual response** — common mismatches: `active` vs `isActive`, `apiKey` vs `key`, `label` vs `name`. Always read the controller's `res.json()` verbatim; do not infer field names from context.
18. **Assuming a `POST` response contains the created record's `id`** — several endpoints (key creation, promotion) return only a token or minimal data with no `id`. If downstream code needs the `id` (e.g. to store in Prisma), make a follow-up `GET` call with the new token and read the id from the list result.
19. **Calling `request.json()` before HMAC verification in a webhook route** — `request.json()` consumes the body stream; the raw body is then unavailable. Always call `request.text()` first, store the raw string, then `JSON.parse()` it. Without the raw body the HMAC signature cannot be verified and every webhook will be rejected or accepted insecurely.
20. **Comparing `notification.issuerId` against local `Issuer.id`** — `notification.issuerId` stores the **API-side** issuer id, not the local one. Match it against `Issuer.apiIssuerId`. Getting this wrong means cert-expiry banners never appear (or appear for the wrong issuer). **Both sides are now UUID strings, so the compiler cannot help here at all** — a local id and an API id are structurally identical and assigning one where the other belongs type-checks cleanly. This is the single most dangerous ID mistake in the codebase and it must be caught by reading, not by `tsc`. Both `fanOutReads()` implementations (`src/app/actions/notifications.ts`, `src/app/api/webhooks/receive/route.ts`) had exactly this bug and now resolve API → local via `apiIssuerId` before touching `UserIssuerAccess`.
21. **Hardcoding `backHref` on a sub-page reachable from more than one parent screen** — e.g. `/invoices/new` and `/invoices/[key]` are linkable from Panel, Comprobantes, and per-type document lists. A fixed `backHref` always returns the user to the same place regardless of where they came from. Use the `?from=<key>` + `BACK_TARGETS` allowlist pattern (`src/lib/back-targets.ts`) instead — see "Back navigation" above — and remember to append `from` on every entry-point link.
22. **Rebuilding a URL from `usePathname()` alone when switching locale** — `UserMenu.handleLocaleChange` in `nav.tsx` used to call `router.replace(pathname, { locale })`, which drops the query string. Any contextual state carried in query params (e.g. `?from=...` for back-navigation) is silently lost on language switch, and the UI quietly falls back to its default. Always append `useSearchParams().toString()` to the path before calling `router.replace`/`router.push` with a new locale.
23. **Catching a non-`ApiError` exception in a Server Action without calling `Sentry.captureException(err)`** — the standard pattern (`docs/guides/coding-guidelines.md → "Adding a Server Action"`) re-throws unknown errors so Next.js's `onRequestError` hook reports them to Sentry automatically. But `bootstrapTenantAction`/`linkExistingTenantAction` in `src/app/actions/onboarding.ts` deliberately catch the post-API-call DB transaction's errors instead of re-throwing, to avoid showing a raw crash page after an external side effect (a live Comprobify API key) already succeeded. Catching instead of re-throwing opts out of automatic Sentry capture — call `Sentry.captureException(err)` explicitly before returning the generic error code, or the failure becomes undebuggable.
24. **Setting `ENCRYPTION_KEY` (or any AES key env var) with `openssl rand -base64 32`** — `getKey()` in `src/lib/crypto.ts` strictly requires a 64-character hex string and throws `ENCRYPTION_KEY must be a 32-byte hex string` otherwise, which surfaces to users as a generic `DB_WRITE_FAILED`/internal-error message with no obvious cause. Always generate with `openssl rand -hex 32`, never `-base64`. (`AUTH_SECRET` and `CONTEXT_COOKIE_SECRET` have no such validation and accept either format.)
25. **Trusting a hand-maintained interface field that nobody re-verified, even on an endpoint already in use** — `Pagination` in `src/lib/api.ts` declared `totalPages: number` for years, but `../comprobify/src/models/document.model.js`'s `findByIssuerId()` only ever returned `{ total, page, limit }`. Nothing caught it because no caller read `.totalPages` until the `/documents/[type]` pager was added — then it silently evaluated to `undefined`, comparisons like `undefined <= 1` resolved to `false` (so the "hide on one page" guard never fired), and the interpolated label rendered with the number blank. Rule 15's verify-against-source step applies to *existing* interface fields too, not just newly added ones — when you're the first consumer of a field, verify it against the controller's `res.json()` before trusting it. `totalPages` is now derived client-side via `getTotalPages({ total, limit })` in `src/components/document-pagination.tsx`.
26. **A Server Action's `redirect()` after a mutation dropping the `?from=` query context** — `createInvoiceAction`/`rebuildInvoiceAction` used to `redirect({ href: \`/invoices/${accessKey}\` })` with no query string at all, so Invoice Detail's own `?from=`-based back-link always fell back to `dashboard` ("Panel") after creating or correcting a document, even when the user had started from a per-type document list. This is the same family of bug as #21/#22 (losing `?from=`/query context across a navigation boundary) but the boundary here is a server-side redirect after a mutation, not a client `router.push`/`Link`. The fix threads a `from?: BackTargetKey` parameter all the way through: the page computes its own validated `backTargetKey` → passes it to `InvoiceForm` → `InvoiceForm` passes it to the Server Action → the Server Action appends `?from=` to its `redirect()` target. Any new Server Action that redirects to a page with a `?from=`-based back-link needs the same parameter — it does not happen automatically.
27. **`next/dynamic(..., { ssr: false })` called directly inside a Server Component, and serving a worker script (e.g. `pdfjs-dist`'s `.mjs` worker) from `public/`** — two related pitfalls hit while adding the PDF preview (the toggle now lives inline in `InvoiceActions`/`InvoicePdfPreview`). First, Turbopack's production build (`npm run build`, not just `npm run type-check`) hard-fails with `ssr: false is not allowed with next/dynamic in Server Components` if the `dynamic()` call is written inline in a page — it must live inside its own Client Component file (see `invoice-pdf-preview-lazy.tsx`). Second, manually copying `pdfjs-dist`'s `pdf.worker.min.mjs` into `public/` and pointing `GlobalWorkerOptions.workerSrc` at that static path failed at runtime with `Setting up fake worker failed: Failed to fetch dynamically imported module` — Next.js's static file server doesn't reliably send a module-compatible `Content-Type` for `.mjs`, and the browser's strict ESM loader rejects it. Fixed by letting the bundler resolve and serve the worker instead: `new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url).toString()`. Don't reach for a `public/` copy for any future web-worker-based library — use the `new URL(..., import.meta.url)` pattern first.

28. **Expecting `error.code` (or any custom `Error` subclass property) to be readable inside `error.tsx`/`global-error.tsx`** — when a Server Component throws (e.g. an unhandled `ApiError`), Next.js serializes only `message` and `digest` across the server→client boundary to the nearest error boundary; custom class properties like `ApiError.code` are stripped, and in production builds `message` itself is redacted to a generic string. `src/app/[locale]/error.tsx` cannot branch on the original API error code — it always renders `apiError.UNKNOWN`. If you need the specific code surfaced to the user, catch the `ApiError` *inside* the Server Component/Server Action (before it becomes an unhandled throw) and pass `error.code` down as a prop or return value instead of relying on an error boundary to recover it.

29. **Expecting `src/app/[locale]/not-found.tsx` to handle every 404, including an invalid `:locale` segment itself** — `[locale]/layout.tsx` calls `notFound()` when `hasLocale()` fails (e.g. a garbage locale code that reached the layout without being redirected by `src/proxy.ts`'s middleware first). Because that throw happens inside the very layout that would otherwise wrap `[locale]/not-found.tsx`, Next.js can't render that boundary for this one case — it bubbles to the framework's built-in default 404 (not locale-aware, unstyled), since there is no root `src/app/not-found.tsx`. This only affects a mistyped/garbage locale segment in the URL; normal unmatched routes and explicit `notFound()` calls from pages (e.g. a missing invoice) are correctly caught by `[locale]/not-found.tsx` since the layout above them already rendered successfully before the boundary kicks in.

30. **Using the `Link` component (from `@/i18n/navigation` or plain `next/link`) inside `not-found.tsx`** — client-side navigation triggered from a `notFound()`-rendered boundary silently no-ops in the Next.js App Router: the href resolves correctly, no console error is thrown, but clicking does nothing (confirmed on this project's Next.js 16 — a long-standing framework bug, see [vercel/next.js#49736](https://github.com/vercel/next.js/issues/49736) and [#59981](https://github.com/vercel/next.js/issues/59981)). `src/app/[locale]/not-found.tsx`'s recovery link uses a plain `<a href={`/${locale}/dashboard`}>` (locale from `getLocale()`) instead, forcing a real browser navigation that bypasses Next's broken soft-nav state for this one boundary. If a future `not-found.tsx`/`global-not-found.tsx` needs a link, use the same plain-`<a>` workaround, not `Link`.

31. **Checking `ApiError.status` for a specific error *code*, instead of `ApiError.code` directly** — `isValidation()` in `src/lib/errors.ts` checked `this.status === 422`, but `../comprobify/src/errors/validation-error.js` extends `AppError` with status **400**, and the API has no 422 anywhere (confirmed in `app-error.js`'s `STATUS_METADATA` map) — so `isValidation()` could never return true. Worse, status 400 is shared by several unrelated codes (`ISSUER_ID_REQUIRED`, `INVALID_STATE_TRANSITION`, `INVALID_FILE_UPLOAD`, a bad `Idempotency-Key` header, etc.), so simply changing the check to `this.status === 400` would have been just as wrong in the other direction. Fixed to `this.code === 'VALIDATION_FAILED'`. Rule 15/25's verify-against-source step applies to convenience methods on `ApiError` too, not just `api.ts` interfaces — a status-code check is only safe when that status is 1:1 with one meaning (404/401/429 are; 400 is not).

32. **`addIssuerDocumentType()` sent `{ code }` in the `POST /v1/issuers/:id/document-types` body, but `../comprobify/src/routes/issuers.routes.js`'s `addDocumentTypeValidator` validates a field named `documentType`** — a long-standing bug in `src/lib/api.ts` (not introduced by any specific feature) that silently `VALIDATION_FAILED`ed every attempt to enable a new document type on an existing issuer via `/issuers`. It went unnoticed because issuers already have document type `01` enabled at creation, so nobody exercised "add a type after the fact" until trying to enable `04` (Nota de Crédito) for an existing issuer. Fixed by sending `{ documentType: code }`. `removeIssuerDocumentType()` was unaffected — it sends `code` as a URL path segment (`DELETE /v1/issuers/:id/document-types/:code`), not a body field, which matches the route. Same family of bug as #17 (trusting a field name instead of reading the validator) — the same rule applies even to endpoints that "work" elsewhere in the app, since each call site can independently get the field name wrong.

33. **Sending an array field (e.g. `documentTypes`, `initialSequentials`) as `JSON.stringify(...)` inside a `multipart/form-data` body and assuming the API will receive it as an array** — `createIssuer()`'s call to `POST /v1/issuers` does this because the same request may also carry a P12 file, which forces multipart encoding. `multipart/form-data` never auto-deserializes a JSON-looking string field back into an array — without a `customSanitizer` on the API side, `express-validator`'s `isArray()` sees the literal string `'["01","04"]'` and rejects it with `VALIDATION_FAILED`, even though the exact same payload shape is correct (and documented) for this endpoint. `../comprobify/src/validators/registration.validator.js` already had the fix (`customSanitizer` that `JSON.parse`s string values before `isArray()`) for the identical fields on `POST /v1/register`; `issuer.validator.js`'s `createBranch` validator just hadn't gotten the same treatment until it was added alongside the issuer create/edit/sequentials work. If a future multipart call needs a new array/object field, confirm the API validator has this sanitizer — don't assume it does just because a sibling endpoint handles the same field name correctly.

34. **Writing a plain object literal or `null` into a Prisma `Json?` column without the right cast** — `Tenant.pendingBankTransfer` (caches the API's one-time `bankTransfer` response, see "Subscription & billing" above) tripped both directions. Setting it ( `data: { pendingBankTransfer: result.bankTransfer } }` ) fails `tsc` with "Index signature for type 'string' is missing" — a hand-written TS interface (`ApiBankTransferInfo`) doesn't structurally satisfy Prisma's `InputJsonObject`; cast through `as unknown as Prisma.InputJsonValue`. Clearing it back to SQL `NULL` (`data: { pendingBankTransfer: null }`) also fails to typecheck — a literal `null` is ambiguous between "store JSON null" and "store SQL NULL" for a `Json?` column, so Prisma requires the explicit `Prisma.JsonNull` sentinel instead. Both `Prisma`/`Prisma.JsonNull`/`Prisma.InputJsonValue` come from `import { Prisma } from '@prisma/client'` (or `import type` for the type-only case).

35. **Using `<Link>` (from `@/i18n/navigation` or `next/link`) for cross-domain navigation between the marketing host and the app host** — Next.js intercepts `<Link>` clicks and issues an RSC prefetch to the href's origin before navigation. When that origin is a different domain (e.g. a link on `staging.comprobify.com` pointing to `app-staging.comprobify.com`), the browser blocks the cross-origin fetch and the link either silently fails or throws a CORS error in the console. This caused every CTA, login, and register link on the marketing site to break when first deployed to the two-domain staging setup. **Always use a plain `<a href="/{locale}/target">` for any link that crosses the marketing ↔ app domain boundary** — the browser then does a full-page navigation that follows the proxy's 301 redirect normally. Links that stay on the same domain (e.g. `/` → `/pricing` on the marketing host, or `/dashboard` → `/invoices` on the app host) are unaffected and can keep using `<Link>`.

36. **Admin API paths omitting the `/v1/` prefix** — `src/lib/admin-api.ts` calls `/v1/admin/tenants`, `/v1/admin/payments`, etc. because `server.js` mounts all routes (including admin) under `/v1` in `routes/index.js`. Paths like `/admin/tenants` return Express's default HTML 404 because no route is registered there. Always check `server.js` → `routes/index.js` for the mount prefix before writing any path in `admin-api.ts`. A non-JSON 404 response now also throws `ADMIN_API_UNREACHABLE` (via the `Content-Type` guard in `request()`) instead of crashing on `JSON.parse()` of the HTML body.

37. **Wrapping the locale layout's unauthenticated/no-tenant branch in a `<main>` element** — the locale layout falls into its `else` branch for users with no tenant (login page, register page, super admin). A `<main className="flex-1">` there looks harmless, but `flex-1` only works inside a flex container and the body is not one, so the `<main>` collapses to auto-height. Any nested layout that relies on `h-full` (e.g. the admin sidebar's `<div className="flex h-full md:flex-row">`) then resolves `h-full` against that collapsed height — the sidebar only grows as tall as its content instead of filling the viewport. The fix is `<>{children}</>` (no wrapper), so the admin layout's `h-full` div sits directly under `<body>` the same way the regular authenticated layout's div does.

39. **Calling `signOut()` from a Server Component or `requireContext()`** — `signOut()` clears the session cookie, which requires writing a `Set-Cookie` header. Server Components run during rendering and cannot write response headers at that point; the call throws at runtime. The only valid contexts for `signOut()` are Server Actions and Route Handlers. When `requireContext()` needs to force a sign-out (e.g. when `User.active === false`), it must redirect to a Route Handler (`/api/auth/signout-disabled`) that calls `signOut()` and then redirects to `/login`. Attempting to call `signOut()` directly inside `requireContext()` or any Server Component produces a runtime error on every authenticated page load for the affected user.

38. **Gating only the page, not the Server Action** — `requirePermission()` on a page shows 404 to unauthorized users navigating to the URL, but a Server Action is a separate POST endpoint that can be called directly without ever visiting the page. A Viewer who knows the action's name can invoke `createInvoiceAction` without hitting `/invoices/new`. Every mutation Server Action must independently call `requirePermission()` at its top, regardless of whether the page that hosts the form already gates access. Similarly, hiding a button in the UI (`canCreate && <Button>`) is a UX convenience, not a security measure — the action gate is the real boundary. The two-layer pattern is: (1) `requirePermission` in the page → blocks the route for unauthorized roles, (2) `requirePermission` in every action → blocks the mutation even if the page is reached, (3) conditional rendering in the Server Component → hides buttons the user can't use.

40. **Using `NEXT_PUBLIC_APP_URL` for anything marketing/SEO-related** — `NEXT_PUBLIC_APP_URL` is the **app** host's origin (used to build callback/webhook/invite URLs, see `src/lib/webhook-url.ts` and `src/app/actions/onboarding.ts`), not the marketing host. `src/lib/seo.ts`'s `MARKETING_BASE_URL` reads a separate `NEXT_PUBLIC_MARKETING_URL` var instead — using `NEXT_PUBLIC_APP_URL` for `metadataBase`/canonical URLs/the sitemap would point every marketing page's canonical/OG URL at `app.comprobify.com` instead of `comprobify.com`, silently wrong even though both vars resolve to *a* valid Comprobify domain. Relatedly, `MARKETING_ROUTES` exists as two independent representations — a regex in `src/proxy.ts` (drives host-based routing/redirects) and a string array in `src/lib/seo.ts` (drives the `robots.ts` allowlist and `sitemap.ts`) — adding a new marketing page requires updating both by hand; there's no shared import between them to keep in sync automatically.

41. **Omitting an optional API parameter that has a *different* default than the local record you write alongside it** — `createTenantApiKeyAction` called `createTenantApiKey(ctx, label)` without the third `environment` argument, so `POST /v1/keys` fell back to its own `'sandbox'` default, while the local `TenantApiKey` row was written with `environment: ctx.tenant.environment`. On a promoted tenant that produced a row labelled `production` holding a key the API treats as `sandbox` — which then 401s with `API_KEY_ENV_MISMATCH` on every route behind `require-matching-environment.js`. Nothing failed at creation time; the key just didn't work, and (before `findAppApiKeyRow()` pinned the selection) it could become the key `requireContext()` handed to the whole app. When an endpoint has an optional field that also exists on the local mirror row, always send it explicitly and persist the value the API returned — never assume the two defaults agree.

42. **`db.findFirst()` with no `orderBy` where exactly one row must be picked consistently** — `requireContext()` resolved the tenant's API key with `findFirst({ where: { tenantId, isActive: true } })`. With one key that's fine; the moment self-service key creation exists, "which row comes back" is unspecified and can change between requests, so the app's own authentication could silently migrate to a key the user minted for Postman (and then revoked). Any `findFirst` that stands in for "the current X" needs an explicit, stable `orderBy` — here `[{ createdAt: 'asc' }, { id: 'asc' }]` inside `findAppApiKeyRow()`, so the same row is also identifiable in the UI as un-revocable.

43. **Assuming a single API error `code` maps to a single meaning, even when it already worked that way for years** — `POST /v1/register` throws `ConflictError` (→ `CONFLICT`) for two unrelated reasons: a RUC already registered under a different email, and (since the register()/recover() split) the caller's own email already having an account. Both hit the exact same status (409) and the exact same `code`, so `bootstrapTenantAction`'s `{ error: err.code }` result can no longer tell them apart — `apiError.CONFLICT` now has to read generically enough to cover both, and can't say "that RUC is taken" the way it used to. This is the same family of trap as #31 (a status/code shared by more than one meaning isn't safe to branch on or word narrowly), but here the ambiguity was introduced by an *upstream* API change to an endpoint this app already called, not by anything in this codebase — rule 15/25/31's "verify against source" step needs re-running whenever the backend's error-handling changes, not just when writing a call site for the first time.

## Git Commit Conventions

Format: `type: short description` (max 72 chars, imperative mood, no period)

| Type | Use for |
|------|---------|
| `feat` | new screen or feature |
| `fix` | bug fix |
| `refactor` | code change with no behaviour change |
| `style` | CSS / styling only |
| `i18n` | translation file changes |
| `docs` | documentation only |
| `chore` | dependencies, tooling, config |
